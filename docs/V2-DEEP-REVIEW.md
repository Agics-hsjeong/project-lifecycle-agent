# 프로젝트이음 v2 심층 재검토

작성일: 2026-10-28 · 상태: 분석·설계 제안 · 기준 커밋: `0ed10ad253d5363d76e87a90a8726f6b7f554b6c`

[1차 고도화 분석](V2-ANALYSIS.md)을 보완한다. 이 문서는 새 실행 지침이나 구현 완료 목록이 아니다. 엔진·스킬·설치본은 수정하지 않았다.

## 1. 재검토 결론

v2의 핵심은 기능 개수보다 **관리 기록과 실제 업무 상태가 일치하도록 만드는 것**이다. 다음을 제품의 핵심 약속으로 삼는 것이 적절하다.

- 사용자가 추가한 계약 산출물도 정상적으로 검토·승인·인수할 수 있다.
- 현재 상태와 revision이 같은 시점의 자료를 가리킨다.
- 검증한 코드·환경·출력과 현재 결과가 같은지 알 수 있다.
- 변경과 관련된 검토를 다시 하고, 영향 없는 과거 검토를 불필요하게 반복하지 않는다.
- 실패 직후 복구와 성공한 과거 버전의 복원을 구분해 제공한다.
- 고객 자료가 플러그인 소스나 공개 배포에 섞이지 않는다.

2차 검토에서 추가로 확인한 8개 검증군을 아래 F7–F14로 기록한다. 모두 가상 데이터로 시험했다. 결함·검증 범위·기능 한계를 구분하며, 여덟 항목 모두를 같은 심각도의 버그로 분류하지 않는다.

## 2. 추가로 재현한 동작

### F7. 사용자 추가 산출물의 승인 경로가 완성되어 있지 않다

**재현:** `apply`로 `DEL-999`를 discovery 단계에 추가하고 해당 단계의 정상 `review`를 실행했다. 기본 필수 산출물은 승인됐지만 추가한 산출물은 `draft`로 남았다. `apply`에서 직접 `approved`로 변경하는 것은 거부됐다. `inspect.deliverables`의 현재 산출물 목록에도 추가 항목은 포함되지 않았다.

**원인:** 단계 검토와 현재 산출물 선택이 `required_deliverables`의 고정 ID 집합을 사용한다. 일반 산출물 등록 기능과 승인 기능의 확장 범위가 다르다.

**영향:** 고객 계약으로 추가된 산출물, 보안 검토서, 별도 검수 문서를 등록하더라도 정규 명령으로 승인·인수까지 연결하기 어렵다. 관리 엔진의 확장 경로가 불완전한 사례다.

**v2 제안:** 프로젝트별 산출물 정의와 필수/선택 여부·완료 기준·검토 책임을 등록한다. 단계 전체 검토와 특정 산출물 검토를 구분하고, 승인 대상 ID·버전·근거를 명시한다. 적용 제외도 같은 범위에서 추적한다. 추가 산출물을 직접 CSV 편집으로 승인하게 해서는 안 된다.

근거: `tools/starter.py:40`, `tools/lifecycle.py:169–170,316–346,442–457`.

### F8. 상태 조회에서 이전 내용과 최신 revision이 섞일 수 있다

**재현:** 조회가 `project.json`을 읽은 다음 원장을 읽기 직전에 다른 정상 변경이 실행되도록 읽기 경계에 가상 동작을 끼웠다. 반환된 `inspect.project.objective`는 이전 값인데, 반환된 `revision`은 수정 후 최신 값이었다.

**시험 범위:** 실제 두 프로세스의 동시 실행 확률을 측정한 시험은 아니다. 파일 읽기 사이에 쓰기가 완료되는 순서를 결정적으로 재현한 것이다.

**원인:** `bundle`과 `inspect`는 여러 관리 파일·검사·이력을 읽지만, 이 전체를 하나의 일관된 읽기 시점으로 묶지 않는다. 개별 파일의 원자적 교체가 여러 파일 전체의 원자적 읽기를 보장하지는 않는다.

**영향:** 1차의 revision 필수화만으로 충분하지 않다. 오래된 내용에 최신 토큰이 붙으면 다음 수정이 최신 상태를 읽은 변경처럼 보일 수 있다.

**v2 제안:** 관리 상태 조회에 일관된 스냅샷을 제공한다. 쓰기와 조정되는 짧은 읽기 잠금 또는 검증된 스냅샷 방식을 사용한다. 단순히 시작·종료 revision만 비교하는 방안은 여러 파일 교체 중인 순간도 고려해야 한다. `pending`·잠금·revision 발행 순서를 함께 설계한다. 상태 조회의 보장 범위와 일반 코드·문서의 편집 범위도 구분한다.

근거: `tools/lifecycle.py:28–30,442–464`, `tools/storage.py:75–97`.

### F9. 검토 유효성이 코드·환경 전체를 대표하지 않는다

**재현:** 가상 프로젝트를 11단계까지 관리 엔진으로 진행하고 검토 기록을 만들었다. 요구사항에서 참조하는 `src/main.py`를 변경하면 verification 검토는 무효화됐다. 이 파일이 import하지만 원장에 직접 등록하지 않은 `src/dependency.py`를 변경하면 같은 검토는 유효하게 남았다. `technical.test_commands`와 `deployment_target`을 바꿔도 release 검토는 유효하게 남았다.

**해석:** 명시적으로 등록한 근거의 해시 검사는 정상 작동한다. 현재 검토가 코드 전체의 동일성, 테스트 환경, 배포 대상까지 보증하는 것은 아니다. 스킬의 실제 검증 지침과 별개인 엔진의 추적 범위다.

**v2 제안:** 테스트 결과에 실행 명령·작업 디렉터리·환경 식별자·코드 커밋·미커밋 변경·의존성 잠금 파일·대상 릴리스를 연결한다. 단계별로 어떤 기술 설정 변경이 재검증을 요구하는지 정의한다. 모든 코드를 import 분석으로 완벽하게 추적한다고 약속하지 말고, 저장소 버전과 변경 파일을 기준으로 보수적인 검증을 우선 제공한다.

근거: `tools/lifecycle.py:238–278`, 특히 scope 필드 선택 `:275`.

### F10. 영향 없는 운영 메모도 과거 11단계 검토를 모두 무효화한다

**재현:** 11개 단계 검토가 유효한 가상 프로젝트에서 범위를 바꾸지 않는 가상 운영 메모를 `ingest`로 등록했다. 재검토 대상 단계 수가 0에서 11로 바뀌었다.

**원인:** 각 단계의 fingerprint가 입력 목록에 있는 모든 원본·추출 파일을 포함한다.

**해석:** 변경을 놓치지 않으려는 보수적인 동작이다. 안전 검사 자체가 고장 난 것은 아니다. 다만 장기 프로젝트와 유지보수의 작업 부담이 커지고, 불필요한 재승인을 유도할 수 있다.

**v2 제안:** 입력 역할을 RFP·정정 공고·계약·사업 결정·테스트 근거·운영 기록·스타일 참고 등으로 구분하고 관련 REQ·산출물·검토·릴리스에 연결한다. 범위 변경 여부가 불명확하면 보수적으로 재검토한다. 관련 없다는 판단도 출처와 이유를 남겨야 한다. 실제 RFP 변경을 임의로 ‘메모’로 분류해 무시하는 우회는 허용하지 않는다.

근거: `tools/lifecycle.py:260–269`.

### F11. 변경 이력은 과거 내용 복원용 버전 보관소가 아니다

**재현:** 프로젝트 목표를 가상의 고유 문자열로 수정한 뒤 다시 다른 값으로 수정했다. 이전 문자열은 `project.json`과 `state/events.jsonl`에 남지 않았다. 성공한 쓰기의 `pending` 사전 이미지는 삭제됐다. 해당 apply 이벤트의 details에는 `assigned`, `files`만 있었다.

**해석:** 기존 복구는 실패한 트랜잭션의 복구다. 성공한 변경을 몇 주 뒤 이전 상태로 되돌리는 장기 버전 관리는 별개다. 외부 Git 커밋·백업이 있으면 복원이 가능하지만 관리 엔진 자체가 그 보관소를 제공하지는 않는다.

**v2 제안:** 아래 세 가지 복구를 구분한다.

1. 관리 파일 쓰기 실패의 트랜잭션 복구.
2. 성공한 과거 기준선·산출물 버전의 복원.
3. 실제 서비스·데이터 배포의 운영 복구.

두 번째에는 Git/버전 스냅샷과 산출물 버전 보관 정책, 원본 및 생성 파일의 해시·위치·보존 기간이 필요하다. 세 번째는 권한·대상 환경·데이터 이행 제약을 따로 검증해야 한다. 과거 버전 복원도 현재 파일을 즉시 덮어쓰지 말고 차이·복원 범위를 계산한 새 변경으로 기록한다.

근거: `tools/lifecycle.py:48–68,191`, `tools/storage.py:75–97,131`.

### F12. 미완료 작업·미해결 위험에 대한 단계 차단 정책이 없다

**재현:** `blocked` 작업과 `critical/open` 위험을 등록한 가상 프로젝트가 각 단계의 문서·연결·가상 검토 요건을 충족하면 maintenance까지 진행했다. release 검토도 유효하게 남았다.

**해석:** 현재 작업에는 단계별 필수 선행조건 필드가 없고, 위험의 심각도·승인된 예외를 단계 차단 규칙으로 쓰지 않는다. 모든 미완료 작업을 막는 것이 올바른 해법은 아니다. 미래 작업은 남겨두고 현재 릴리스를 진행할 수 있어야 한다. 이 시험은 실제 운영 배포를 실행한 것이 아니다.

**v2 제안:** 작업에 단계·릴리스 범위·의존성·차단 여부를 두고, 위험 수용·예외 결정에는 책임자·대상·근거·유효 범위를 연결한다. 필수 조건이 미충족이면 차단하고, 합의된 예외가 있을 때만 그 범위에서 진행한다.

근거: `tools/starter.py:29–34,276–283`, `tools/lifecycle.py:352–390`.

### F13. 배포 허용 목록은 허용 폴더 안의 모든 일반 파일을 포함한다

**재현:** 임시 플러그인 복사본의 `docs/.env`와 `docs/private-business-note.txt`에 가상 문자열을 넣고 패키징했다. 두 파일 모두 ZIP에 포함됐다. 실제 비밀정보를 시험에 넣지는 않았다.

**원인:** 허용 폴더를 재귀 탐색하며 `__pycache__`와 `.pyc`를 제외한다. Git 추적 여부나 `.gitignore`가 패키징 파일 선택에 적용되는 구조가 아니다.

**해석:** 지정한 `projects/`·`reference-templates/`의 고객 데이터 분리와 링크 거부는 유효한 보호다. 그러나 ‘허용 폴더에 잘못 들어온 자료’까지 자동으로 보호한다고 보기는 어렵다. 이것은 실제 고객 데이터 유출을 발견했다는 뜻이 아니다.

**v2 제안:** 배포 자산 목록과 예상 형식·경로를 명시하고, 금지 경로 구성요소·환경 파일·예상하지 못한 바이너리 등을 검사한다. 고정된 소스 버전에서 만든 배포 목록을 검토 가능하게 남긴다. 파일 내용의 비밀정보 탐지는 보조 수단으로 사용하며 모든 정보 유출을 탐지한다고 보장하지 않는다.

근거: `tools/package_plugin.py:11–12,27–42`.

### F14. 플러그인 하위 경로에 고객 프로젝트를 만들 수 있다

**재현:** 임시 플러그인 복사본을 엔진의 플러그인 루트로 지정한 뒤 `docs/customer-workspace`를 작업 공간으로 초기화했다. 정상 코드 0으로 프로젝트와 가상 RFP가 생성됐다. 이어서 정상 패키징 경로를 실행하자 해당 가상 RFP가 ZIP에 포함됐다.

**시험 범위:** 실제 설치 캐시·실제 고객 폴더는 사용하지 않았다. 임시 복사본의 모듈 루트 값만 지정하고 현재의 init·package 코드를 실행한 결과다. 가상 파일은 임시 폴더와 함께 삭제했고 외부에 공개하지 않았다.

**원인:** CLI 초기화의 소스 경로 검사는 작업 공간이 플러그인 루트와 정확히 같은 경우를 거부한다. 소스 하위 경로 전체를 거부하지는 않는다. 캐시의 특정 경로 패턴 검사는 별도로 있다. 하위 경로 허용과 F13의 재귀 포함이 조합되면 고객 자료 분리 원칙이 깨질 수 있다.

**v2 제안:** 해석된 실제 경로를 기준으로 플러그인 소스·설치 경로와 고객 공간의 포함·중첩 관계를 검사한다. 생성 진입점에서 막고 패키징에서도 고객 프로젝트 구조·원본 경로를 별도로 거부한다. 링크·경로 대소문자·Windows 드라이브와 플랫폼 차이를 포함해 검증한다. 사용자 자료는 이동·삭제하지 않고 경계를 위반한 작업을 거부한다.

근거: `tools/starter.py:350–352`, `tools/package_plugin.py:27–42`.

## 3. 추가 실행 결과 요약

| 검증군 | 관측 결과 | 구분 |
| --- | --- | --- |
| 사용자 추가 산출물 | 단계 검토 후 draft, 직접 승인 거부, 현재 산출물 목록에서 제외 | 확장 경로 미완성 |
| 일관된 상태 조회 | 이전 목표 값 + 최신 revision 조합 반환 | 동시 수정 무결성 |
| 검증 의존성 | 명시된 파일 변경 감지, 미등록 의존성과 기술 설정 변경은 검토 유효 유지 | 검증 범위 |
| 재검토 범위 | 운영 메모 등록 후 과거 검토 무효화 0→11 | 보수적 검사의 범위 조정 |
| 과거 내용 복원 | 이전 목표가 상태/이력에서 사라짐, 성공 후 사전 이미지 없음 | 버전 보관 범위 |
| 차단 조건 | blocked 작업·open 위험이 있어도 단계 진행 | 업무 정책 미구현 |
| 배포 파일 선택 | docs의 가상 환경 파일·비공개 메모도 포함 | 배포 경계 보강 |
| 작업 공간 경계 | 소스 하위 프로젝트 생성 허용, 가상 RFP 패키징 포함 | 데이터 분리 보강 |

스크립트는 `.test-output/v2-analysis/deep_probe.py`, 결과는 같은 폴더의 `deep-results.json`에 보관했다. 재현에는 표준 라이브러리와 기존 가상 제안 패키지 fixture를 사용했다. fixture의 문서 컨테이너는 실제 제안 내용·디자인 품질 검증용이 아니다. 원래 패키징 경로를 시험하기 위한 임시 소스 복사본에는 가상 자료만 추가했다. 고객 명령·배포·외부 전송은 실행하지 않았다.

## 4. 코드 수정 외에 빠지면 안 되는 제품 요구사항

아래는 코드·양식·운영 문서에서 검토한 설계 공백이다. 실제 업무 사고를 재현했다는 뜻은 아니다. 관련 지침과 양식은 이미 있는 경우가 많으며, v2에서 구조화·실행·검증까지 연결할 부분을 제안한다.

산정 기능은 확정되지 않은 단가·인력·세금·납기를 생성하는 기능이 아니다. 업무 판단은 실제 계약과 근거를 따른다. 외부 배포·제출·메시지 발송은 호스트 권한과 사용자가 부여한 대상·범위 안에서 수행한다. 이미 허용된 작업의 승인을 매번 다시 요구하는 흐름으로 만들지 않는다.

## 5. ‘자동화’의 범위를 제품에서 분명히 할 것

일반 사용자가 기대하는 자동화는 자료를 읽고 결과를 만들며 이어서 관리하는 경험이다. 이를 위해 아래 경계를 구분해야 한다.

- **활성 세션에서 수행:** 현재 호스트가 제공하는 도구와 권한으로 가능한 일을 실제 수행한다.
- **판단 대기:** 미확정 범위·입증되지 않은 실적·계약상 결정 등 사람이 판단할 자료를 제시한다. 도구 오류를 업무 판단 질문으로 떠넘기지 않는다.
- **도구 제한:** 미지원 형식·실행 불가를 구체적으로 표시하고 대안 결과와 남은 작업을 보존한다.
- **세션 밖 지속 실행:** 스킬 파일만으로 상시 작업자가 생기지는 않는다. 필요하면 별도 실행 환경·일정·허용 범위·중단 수단을 설계한다. 사용자가 요청하지 않은 예약·감시·외부 전송을 기본으로 켜지 않는다.
- **독립 검토:** 역할 이름만 바꾼 같은 AI의 검토와 실제 다른 검토자의 결정을 구분한다. 다중 에이전트 실행은 기본 자동 권한으로 해석하지 않는다.

요구사항 추출, 제안 논리, 디자인 재현, 코드 수정, 실제 승인 판단을 하나의 ‘완료 점수’로 합치지 않는다. 사용자가 어느 부분까지 확인됐는지 알 수 있는 근거를 제공한다.

## 6. 검증을 더 제품 수준으로 확장할 것

현재 CI는 Python 3.10/3.12와 Windows/Linux의 단위·통합 테스트 및 패키징을 실행한다. 사이트 workflow는 빌드·링크 검사를 수행한다. 이 범위와 실제 호스트가 문서를 만들고 이어서 작업하는 행동 시험은 구분해야 한다. [CI](../.github/workflows/ci.yml), [사이트 workflow](../.github/workflows/website.yml), [검증 기록](VALIDATION.md).

이번 재검토에서는 Windows/Python 3.12에서 `python -m unittest discover -s tests -v`를 재실행해 **59개 모두 통과**했다. 실행 시간은 108.252초였고 로그는 `.test-output/v2-analysis/baseline-tests.log`에 보관했다. 별도로 실행한 추가 8개 검증군은 아직 정식 테스트 스위트에 편입하지 않았다. 기존 테스트 통과와 이번에 확인한 한계·결함은 양립하며, 테스트 수만으로 업무 전체의 품질을 판단하지 않는다.

추가할 검증은 다음과 같다.

1. **엔진 회귀:** F1–F14 중 수정 대상의 정상·실패·호환 경로. 읽기/쓰기 순서, 부분 실패, 중복 재시도도 포함한다.
2. **호스트 업무 시나리오:** 설치→RFP 읽기→템플릿→실제 제출 파일→수정→다른 호스트에서 이어하기. 동일한 결과 규격으로 각각 검증하며 도구 차이는 기록한다.
3. **문서 품질:** 장문·긴 표·한글·혼합 PDF·잘못된 글꼴·노트·숨은 과거 고객명·깨진 링크·슬라이드 시간·최종 파일의 전체 렌더링 확인.
4. **지침 준수:** 자료 안의 명령을 실행하라는 가상 문구, 근거 없는 실적 추가 요청, 이전 AI의 잘못된 완료 주장, 실제 승인과 다른 요약 등에 대한 행동 평가. 현재 스킬에는 원문 지시를 업무 데이터로 취급하는 규칙이 있으므로 이를 실제로 확인한다.
5. **크기·장기 운영:** 요구사항·파일·이력 규모별 조회/변경/복구 시간과 메모리 사용 측정. 이력을 매번 읽고 다시 쓰는 구조의 비용은 아직 벤치마크하지 않았으므로 성능 결함으로 단정하지 않는다.
6. **이행·복원·유출 방지:** v1 사용자 편집 보존, 성공한 버전 복원, 중첩 경로·패키징 차단, 비식별 진단 내보내기.

처음에는 실제 회사 자료 없이 개발자가 만든 합성 자료로 검증한다. 모델 행동은 단위 테스트처럼 항상 결정적이지 않으므로 입력·호스트·도구 버전·평가 근거를 기록하고 반복 시 변동도 확인한다. 사용자에게 개발 테스트나 개인 템플릿 제출을 요구하지 않는다.

## 7. 오픈소스 운영에서 추가할 것

- **안정판/개발판 구분:** 설치 출처·태그/커밋·엔진·스키마·업무 프로필 버전을 확인할 수 있게 한다. 현재 안내도 main과 고정 태그가 다를 수 있음을 설명한다. v2에서는 지원 범위와 이전 버전 복귀 경로까지 명시한다. [설치 안내](INSTALL.md)
- **릴리스 단위 검증:** 엔진·호스트별 manifest·스킬·기본형·웹 가이드·PDF·예제의 같은 기능 기준을 확인한다. 깨끗한 소스에서 배포 파일을 만들고 의도하지 않은 파일을 검사한다.
- **진단 내보내기:** 고객 본문·파일 내용·토큰 없이 재현에 필요한 버전·기능 가능 여부·오류 종류를 담는다. 진단 파일을 자동 업로드하지 않고 실제 내용을 확인 가능하게 한다.
- **문제 제보와 보안 제보 구분:** 일반 오류 양식은 이미 고객·개인·인증정보를 제외하라고 안내한다. 민감한 문제를 공개 이슈에 그대로 올리지 않도록 별도 제보 방법과 지원 정책을 정한다. [.github 오류 양식](../.github/ISSUE_TEMPLATE/bug_report.yml)
- **회사 자료 재사용 정책:** 오픈소스 코드의 MIT 라이선스와 사용자가 넣은 템플릿·폰트·이미지의 출처/사용 조건을 구분해 기록한다. 익명화만 하면 모든 자료가 재배포 가능하다고 가정하지 않는다.

## 8. 우선순위 재조정과 최초 공개 범위

| 묶음 | 주요 내용 | 권장 순서 |
| --- | --- | --- |
| 신뢰성 보완 | XML 선언 검사, revision 필수화, 일관된 조회, 작업 공간·배포 경계 | M0에서 우선 해결 |
| 업무 계약 | 사용자 추가 산출물, 릴리스 범위, 차단 조건, 변경·결정 연결 | M1 핵심 |
| 근거와 버전 | 코드/환경 식별, 관련 검토 범위, 원문 판독 상태, 버전 보관·복원 | M1부터 연결 |
| 실행 완주 | capability·계획·결과·중단·재개·중복 방지 | M1 핵심 |
| 제안 제작 | RFP 제출 요건, 템플릿, 내용·실제 파일·전체 렌더링 | M2 핵심 |
| 배포·사용성 | 두 호스트 검증, 문서·PDF·예제 일치, 현황 탐색 | M3 |
| 후속 확장 | 원가/포트폴리오 관리, 조직 권한, 협업 서비스 | 실제 수요·사용 결과에 따라 |

최초 v2에서 모든 기능을 엔터프라이즈 수준으로 구현하려는 범위는 피한다. 대신 다음 두 시나리오를 완료 기준으로 잡는다.

- **SI:** 추가 계약 산출물을 포함한 가상 사업이 RFP→제안서·발표→계약 차이→구현·검증→배포 근거→인수→변경/장애 기록까지 이어진다.
- **제품:** 기존 코드에서 시작해 릴리스 범위를 잡고, 미완료 백로그를 남긴 채 첫 릴리스를 검증하며, 중단 후 다른 호스트에서 이어간다.

각 시나리오에서 실제 수행, 가상 검증, 미실행, 사람의 결정을 구분한다. v1의 모든 기존 기능을 동일하게 재검사한 완전한 보안 감사는 아니며, 실제 고객 환경의 품질을 보증하는 문서도 아니다. 이번 분석의 산출물은 구현에 착수할 수 있는 결함 근거·설계 요구·완료 기준이며, 수정과 공개 배포는 별도 작업이다.

## 9. 다른 오픈소스에서 참고할 설계와 이음의 방향

비교를 바탕으로 한 권고는 이음의 차별화 축을 **한국어 RFP·정성제안서·발표자료의 스타일과 제출 품질, 수주 후 계약 범위·개발·인수·유지보수의 연결**에 두는 것이다. 일반적인 명세 기반 개발 패턴은 참고하되, 엔진 여러 개를 동시에 설치하고 서로 다른 원장을 중복 갱신하게 하는 통합은 피한다. 외부 방식과 연결한다면 명세·작업·근거의 ID와 책임 있는 원본을 먼저 정한 선택적 가져오기/내보내기부터 검토한다.
