# 프로젝트이음 v2 고도화 분석안

작성일: 2026-10-28 · 상태: 검토 제안 · 기준 커밋: `0ed10ad253d5363d76e87a90a8726f6b7f554b6c`

후속 분석: [v2 심층 재검토](V2-DEEP-REVIEW.md). 두 번째 검토에서는 가상 시나리오 8개 검증군을 추가해 사용자 추가 산출물의 승인, 일관된 상태 조회, 검증 의존성, 재검토 범위, 이력 복원, 작업·위험 차단 정책, 배포 파일 선택, 작업 공간 경계를 확인했다. 특히 **상태 조회의 일관성, 고객 작업 공간의 하위 경로 분리, 배포 대상 파일 검사**를 초기 보강 범위에 추가한다. 아래의 1차 권고는 후속 분석의 범위·우선순위 조정과 함께 읽는다.

이 문서는 현재 제품을 1세대(v1)로 보고 다음 세대를 제안한다. 현재 플러그인 엔진의 실제 버전은 **0.5.1**, 사이트 패키지 버전은 **1.0.0**이다. 제품 세대와 패키지 버전은 구분한다. 아래 기능·명령·구조는 별도 표시가 없으면 v2 제안이며 현재 지원 기능을 뜻하지 않는다.

## 1. 권고 결론

**v2의 중심을 ‘업무 자료를 이해하고, 다음 작업을 실행하며, 실제 결과와 근거를 남겨 이어서 일할 수 있는 프로젝트 에이전트’로 잡는 것을 권고한다.**

현재는 원본·원장·승인·단계를 안전하게 관리하는 기반이 있다. 다만 무엇을 어떤 도구로 실행하고, 결과의 내용·디자인을 어떻게 확인하며, 실패한 작업을 어디부터 이어갈지는 호스트 AI가 지침을 해석해 수행하는 비중이 크다. 사용자가 원한 ‘자료를 넣고 요청하면 알아서 진행하며 필요한 업무 판단만 받는 경험’을 완성하려면 이 부분을 제품의 명시적인 실행 구조로 만들어야 한다.

우선순위는 **신뢰성 보강 → 방법론·반복 개발의 실제 동작 → 실행·재개 기록 → 제안서·발표자료 제작과 검수 → 현황 화면·협업 연결**이다. 제안 제작과 실행 구조는 함께 설계하되, 모든 협업 서비스나 중앙 서버를 처음부터 구축하지 않는다.

## 2. 분석 범위와 증거

- `tools/`, `blueprint/`, 스킬·참조 문서, 테스트, 설치·검증 기록, 공개 사이트 소스를 검토했다.
- 현재 코드에 가상 프로젝트와 가상 문서만 넣어 여섯 가지 동작을 추가 확인했다. 실제 고객 데이터나 회사 템플릿은 사용하지 않았다.
- 추가 확인 스크립트와 원시 결과는 Git 제외 영역인 `.test-output/v2-analysis/`에 보관했다. 재현 조건과 결과는 이 문서에도 남긴다.
- 기존 검증 기록은 자동 테스트 59개와 설치·패키징·사이트 검증을 포함한다. 1차 분석에서는 전체를 재실행하지 않았고, 후속 심층 분석에서 Windows/Python 3.12의 59개 테스트를 다시 실행해 모두 통과했다. 신규 가상 재현과 기존 테스트의 범위는 구분한다. [기존 검증 기록](VALIDATION.md), [후속 검토](V2-DEEP-REVIEW.md)
- 실제 고객의 업무 성공률, 제안서 수주 효과, 시간 절감률, 다양한 실물 템플릿의 재현 품질은 측정하지 않았다. 코드 구조만으로 이를 보장하지 않는다.

## 4. 실제로 확인한 우선 개선 지점

### F1. 방법론 선택이 엔진의 단계·산출물 기준을 바꾸지 않는다

- **확인:** SI/Product × waterfall/agile/hybrid의 6개 조합에서 단계별 필수 산출물 행렬은 모두 같았다. 단계는 11개다.
- **해석:** 현재 문서도 방법론을 관리 표기로 설명한다. 결함이라기보다 구현된 범위의 한계다. 업무 설명과 적용 제외는 조정할 수 있지만, 방법론별 반복 실행을 엔진이 관리하지는 않는다.
- **영향:** 자체 제품의 여러 릴리스, 일부 기능만 배포하는 반복 개발, UI 없는 사업에도 공통 단계와 전체 요구사항 기준이 적용된다. 문서에 적은 반복 개발과 시스템이 판단하는 완료 범위를 맞추기 어렵다.
- **제안:** 사업 생애주기와 기능·릴리스 반복 주기를 분리한다. 요구사항을 현재 승인된 릴리스 범위에 연결하고, 이후 백로그 때문에 현재 릴리스 검증이 막히지 않게 한다. 프로필별 차이는 이름뿐 아니라 생성 작업·필수 증거·완료 기준에서 검증한다.
- **근거:** `tools/starter.py:16,40`, `tools/starter.py`의 단계별 요구사항 검사, `blueprint/process/WORKFLOW.md:44`.

### F2. revision을 생략하면 오래된 수정이 최신 값을 덮을 수 있다

- **확인:** B가 먼저 수정한 뒤 A가 이전 revision을 명시하면 거부됐다. A가 `expected_revision`을 생략하면 같은 항목의 최신 값을 덮을 수 있었다.
- **해석:** 파일 잠금과 명시적인 충돌 검사는 이미 있다. 스킬도 revision 사용을 지시한다. 다만 엔진이 누락을 허용하므로 지침을 따르지 않는 호출을 막지 못한다.
- **영향:** 두 호스트나 여러 세션에서 이전 상태를 바탕으로 작업할 때 갱신 내용이 사라질 수 있다.
- **제안:** 상태 변경 API의 예상 revision 또는 동등한 동시성 토큰을 필수화한다. 초기 생성·복구·기존 호출자 이행 규칙도 함께 정의한다. 잠금 확보 후 토큰을 확인하고 불일치 시 재조회·차이 검토로 돌린다.
- **완료 기준:** 토큰 누락·오래된 토큰은 기록과 파일을 바꾸지 않고 거부하고, 충돌 없는 갱신만 반영한다.
- **근거:** `tools/lifecycle.py:110–119`.

### F3. PDF의 기본 형식 검사는 실제로 열리는 문서인지 확인하지 않는다

- **확인:** `%PDF-` 헤더 뒤에 임의 문자열만 있는 불완전한 파일이 `check_export`의 PDF 기본 검사를 통과했다.
- **해석:** 해당 함수는 기본 컨테이너 검사라고 명시돼 있다. 이 결과가 전체 제안 승인이나 제출 완료까지 통과했다는 뜻은 아니다. 스킬에는 별도 렌더링·시각 검수 지침이 있다.
- **영향:** 파일 존재·기본 검사와 실제 제출 가능 상태 사이에 간격이 있다. 호스트가 검수 절차를 빠뜨리면 관리 기록만으로 구별하기 어렵다.
- **제안:** 실제 파싱 성공·페이지 수·렌더링 완료·전체 페이지 목록·확인 결과를 별도 증거로 받는다. 필요한 도구가 없으면 ‘검증 불가’로 남기며 제출 준비 완료로 표시하지 않는다.
- **완료 기준:** 손상 PDF를 거부하고, 출력 파일 해시와 전체 페이지 렌더링 목록이 맞지 않으면 검수 완료를 인정하지 않는다.
- **근거:** `tools/proposal.py:73–83`.

### F4. XML 선언 차단이 입력 경로에 따라 다르게 동작한다

- **확인:** 작은 내부 엔터티를 가진 가상 UTF-16 DOCX XML을 입력 추출기에 넣으면 DTD 차단을 지나 엔터티 문자열이 본문에 포함됐다. 참고 템플릿 분석기는 널 바이트를 제거해 선언을 검사하는 별도 구현을 가진다.
- **해석:** 안전한 내부 문자열로 검사했다. 외부 파일 접근·정보 유출·자원 고갈을 재현한 것은 아니다. 확인된 문제는 거부하려던 선언에 대한 인코딩별 처리 불일치다.
- **제안:** 입력·템플릿·제출 검사에서 공유하는 XML 판독 정책을 만들고 지원 인코딩, 선언 거부, 압축 해제 크기·개수·시간 제한을 일관되게 적용한다. 현재 표준 라이브러리 원칙을 유지하며 필요한 외부 제작 도구와 관리 엔진을 분리한다.
- **완료 기준:** 지원 인코딩별 DTD/엔터티 선언은 일관되게 자동 추출을 거부하고, 원본은 보존한다. 정상 문서는 계속 읽힌다.
- **근거:** `tools/intake.py:41`, `tools/template_analysis.py:20–27`.

### F5. 텍스트와 스캔이 섞인 PDF의 부분 누락이 구조화되지 않는다

- **확인:** 텍스트 1페이지와 글자가 이미지로 들어간 1페이지로 만든 PDF에서 실제 추출 텍스트는 1페이지만 있었다. 전체 상태는 `extracted`였고, 페이지별 추출·OCR 확인 상태는 반환하지 않았다.
- **해석:** 원본과 대조하라는 주의 문구는 있다. 엔진이 모든 페이지를 읽었다고 명시적으로 주장한 것은 아니다. 그러나 자동 작업이 읽지 못한 페이지를 정확히 찾을 구조가 부족하다.
- **영향:** RFP의 스캔 표·평가 기준·첨부 조건이 요구사항 분석에서 누락될 수 있다.
- **제안:** 페이지별 `text/needs_ocr/needs_review/confirmed_blank/failed` 등 상태와 근거 위치를 둔다. 텍스트가 없다는 사실만으로 빈 페이지로 판단하지 않는다. OCR 후에도 결과와 원문을 확인한다.
- **완료 기준:** 일부 페이지 미판독 시 전체 읽기 완료로 진행하지 않고, 해당 페이지를 다음 작업으로 반환한다.
- **근거:** `tools/intake.py:46–56`.

### F6. 환경 준비 완료와 실제 업무 수행 가능 여부가 구분되지 않는다

- **확인:** `doctor`의 준비 검사는 Python·식별자·버전·스킬·양식에 관한 5개 항목이다. 프로젝트 지정 시 잠금·미완료 트랜잭션도 확인한다. DOCX/PPTX 제작, PDF 렌더링, OCR, 한글 폰트 등은 검사 항목이 아니다.
- **해석:** 현재의 `ready`는 패키지·관리 엔진 준비 상태로 유효하다. 제안서 제작까지 가능한지 알려주는 진단은 별도로 필요하다.
- **제안:** 업무별 capability를 `available/unavailable/unknown`으로 보고한다. Python에서 확인할 수 있는 항목과 호스트 세션에서 실제 도구 호출로 확인해야 하는 항목을 구분한다. Codex·Claude Code가 동일한 도구를 제공한다고 가정하지 않는다.
- **완료 기준:** ‘RFP 분석 가능 / PPTX 생성 미확인 / PDF 렌더러 사용 불가’처럼 설명하고, 에이전트가 지원되는 대안이나 구체적인 차단 사유를 제시한다.
- **근거:** `tools/lifecycle.py:466–479`.

| revision 명시/누락 비교 | 오래된 값은 명시하면 거부, 생략하면 반영 | 데이터 무결성 보강 |
| 헤더만 있는 PDF | 기본 PDF 검사 통과 | 검증 범위 확대 |
| UTF-16 XML 내부 엔터티 | 입력 추출 경로에서 문자열 확장 | 입력 검사 일관성 수정 |
| 텍스트+이미지 PDF | 2페이지 중 1페이지 텍스트, 전체 `extracted` | 판독 범위 추적 |
| 업무 도구 진단 | 기본 5항목 준비, 제작·OCR capability는 미제공 | 환경 진단 확장 |

재현은 임시 폴더 안에서 수행했고 가상 고객 프로젝트는 종료 시 삭제했다. PDF 혼합 페이지 시험에는 선택적인 pypdf, 가상 문서 제작에는 reportlab·Pillow가 있는 번들 Python 환경을 사용했다. 이 라이브러리들을 관리 엔진의 새 필수 의존성으로 추가한 것은 아니다.

## 5. v2의 사용자 경험

사용자는 파일을 넣고 업무를 요청한다. 환경 준비·원장 갱신·테스트·파일 제작은 에이전트가 수행하고, 예산·범위·수주 판단·대외 제출·운영 승인처럼 책임 있는 업무 판단이 필요한 시점에 판단 자료를 제시한다. 기존에 허용받은 작업의 승인을 반복해서 요구하지 않는다.

### 예시 A: SI 제안부터 납품까지

1. 사용자가 ‘이 RFP로 시작하고, 이전 제안서와 발표자료 스타일을 참고해줘’라고 요청한다.
2. 원본과 참고자료를 프로젝트 공간에 분리 보존하고, 읽은 페이지·읽지 못한 페이지·평가항목·필수 제출물을 정리한다. 미판독 자료는 가능한 도구로 보완한다.
3. 참고자료의 스타일, 목차 구성, 설득 방식, 근거 표현을 분석한다. 과거 고객명·실적·수치·계약 조건은 새 사업의 사실로 복사하지 않는다. 입증되지 않은 사실은 확인 대상으로 표시한다.
4. 평가 기준에 대응하는 제안 전략·목차·장별 핵심 주장과 근거를 잡고, 그 내용에서 제안서와 발표 흐름을 함께 만든다.
5. 실제 DOCX/PPTX/PDF를 만들고 전체 페이지·슬라이드를 렌더링해 넘침·글꼴·표·스타일·평가 대응·발표 시간을 확인한다. 수정 후 다시 확인한 증거를 남긴다.
6. 수주 시 제안 범위와 최종 계약의 차이를 변경 기록으로 남기고, 요구사항·일정·설계·작업으로 연결한다.
7. 구현·테스트·배포는 호스트가 권한 내에서 실행한다. 실패한 작업은 실행 로그와 파일 상태를 기준으로 이어가며, 코드 커밋·테스트·배포 버전·인수 산출물을 연결한다.
8. 운영 장애와 추가 요구는 원래 요구사항·릴리스·수정·회귀 검증에 연결한다.

### 예시 B: 자체 제품 또는 기존 서비스 개선

- ‘RFP 없이 고객 가설과 기존 코드로 MVP를 만들어줘’로 시작한다. 외부 입찰용 제안 패키지는 기본으로 강제하지 않는다.
- 가설·성공지표·백로그를 만들고 첫 릴리스에 포함할 범위를 확정한다. 아직 계획 중인 기능은 현재 배포의 완료 판정을 막지 않는다.
- 주기마다 기획·구현·검증을 반복하고, 결과에 따라 다음 범위와 가설을 조정한다.
- 기존 프로젝트는 현재 파일과 Git 이력·도구 환경을 먼저 파악하고 관리 정보를 추가한다. 새 기본형을 덮어쓰지 않는다.

## 6. 제안하는 구조

```text
Codex / Claude Code의 자연어 진입점
  → 호스트별 도구 가능 여부·결과 규격
  → 계획 / 단계 실행 기록 / 중단·재개 조정
  → 업무 프로필 + 사업 단계 + 릴리스·반복 범위
  → 트랜잭션 상태 + 원본·산출물·검증 근거
       ↔ 문서·발표·코드·테스트·배포 작업
       → 로컬 현황 화면 / 선택적 외부 서비스 연결
```

### 핵심 설계 원칙

1. **관리 엔진과 호스트의 실행 책임을 명확히 한다.** 엔진은 계획·상태·증거의 규칙을 관리하고 호스트는 사용 가능한 도구를 실행한다. 호스트에 없는 기능을 스킬 문구만으로 제공할 수 있다고 표시하지 않는다.
2. **논리 역할과 실제 에이전트 실행을 구분한다.** PM·기획·디자인·QA 역할은 한 호스트가 순차 수행할 수 있다. 역할 문서가 하위 에이전트 실행 권한을 주지 않는다. 병렬 위임은 명시적인 사용자 요청이나 적용 지침이 있을 때만 한다.
3. **업무 상태와 실행 상태를 분리한다.** 프로젝트의 제안/수주/보류/실주/진행/종료 상태와 개별 작업의 실행·실패·판단 대기 상태는 별개다. 사업 단계는 유지하되 반복 주기를 그 안에서 운영한다.
4. **한 번의 실행을 추적할 수 있게 한다.** 실행 ID, 입력 revision, 작업 범위, 필요한 도구, 결과 파일, 검증 결과, 재시도 키, 중단 사유를 남긴다. 성공 표시에는 실제 결과가 필요하다.
5. **근거의 존재와 의미를 나눠 검사한다.** 파일 해시·경로·커밋·검사 결과는 기계적으로 확인한다. 제안의 설득력이나 실제 승인 여부는 출처가 있는 검토 기록으로 남긴다. 같은 AI의 자기 검토를 독립된 사람의 승인으로 표현하지 않는다.
6. **데이터 원본은 하나로 둔다.** 초기에는 기존 파일과 트랜잭션 기반을 확장하는 것이 이행 위험이 작다. DB 전환은 규모·조회·동시 작업 요구를 측정한 뒤 판단한다. DB와 CSV를 각각 수정 가능한 이중 원본으로 두지 않는다.
7. **공개 사이트와 고객 작업 공간을 분리한다.** 공개 사이트는 소개·설치·가이드다. 고객 자료가 들어가는 현황 화면은 로컬을 기본으로 하고 공개 Pages에 올리지 않는다.

초기 데이터 모델은 `실행·단계 결과`, `릴리스/반복 범위`, `근거·원문 위치`, `업무 결정`부터 추가한다. 변경·장애는 기존 작업·요구사항과 연결하는 최소 구조부터 시작한다. 모든 개체의 관리 화면과 외부 API를 동시에 만드는 범위는 피한다.

## 7. 제안서·발표자료 고도화의 구체 범위

| 구성 | 필요한 동작 | 확인 기준 |
| --- | --- | --- |
| 원문 이해 | 페이지·절·표 단위 출처와 판독 상태 | 누락 페이지가 작업 목록에 드러남 |
| 제안 내용 | 평가 기준→핵심 주장→입증 근거→본문·슬라이드 연결 | 모든 적용 평가항목의 대응 위치와 미확인 사실을 찾을 수 있음 |
| 참고 패턴 | 전체 테마와 장별 레이아웃·표현 패턴 구분 | 어떤 원본의 어느 부분을 참고했는지 추적 가능 |
| 사실 보호 | 기존 자료의 실적·인력·수치를 검증 대상과 분리 | 과거 고객 정보를 새 사업의 사실로 자동 전용하지 않음 |
| 파일 제작 | 지원되는 실제 문서·발표 제작 도구 연결 | 편집 가능한 출력과 제출본이 실제로 열림 |
| 시각 검수 | 전체 페이지·슬라이드 렌더링 목록, 확인·수정 이력 | 일부 샘플 확인으로 전체 검수 완료를 표시하지 않음 |
| 발표 준비 | 장별 메시지·대본·시간·예상 질문·근거 | 본문·슬라이드·대본 사이 핵심 수치와 약속이 일치 |
| 제출 확정 | 산출물 버전·해시·검증 결과·업무 결정 묶음 | 수정 후 이전 검수 결과를 그대로 재사용하지 않음 |

HWP 전용 편집, 복잡한 마스터·차트·글꼴의 완전 재현은 사용 환경과 제작 도구 검증이 필요하다. 지원하지 않는 기능은 ‘동일하게 재현됨’으로 표시하지 않고 지원 형식·대체 결과·차이를 분명히 한다. 근거 없는 단일 ‘AI 품질 점수’보다 읽기·평가 대응·사실·시각 품질을 각각 확인하는 방식이 유용하다.

## 8. 우선순위와 개발 완료 기준

| 우선순위 | 묶음 | 완료 기준 |
| --- | --- | --- |
| P0 | 입력·수정 신뢰성 | F2·F4 회귀 검증, 원본 보존, 충돌 때 무변경 확인 |
| P0 | 판독·출력 검증 | F3·F5·F6 처리, 미판독·미검증을 완료로 오인하지 않음 |
| P0 | v1 이행 설계 | 변경 미리보기·백업·ID/이력 보존·복구 시험 |
| P1 | 업무 프로필·릴리스 범위 | SI·제품·UI 없는 사업·유지보수의 작업 및 완료 기준이 실제로 구분됨 |
| P1 | 계획·실행·재개 | 중단된 작업 재개, 중복 파일/기록 방지, 필요한 업무 판단만 대기 |
| P1 | 제안·발표 제작 | 가상 RFP+참고 템플릿에서 실제 출력과 전체 렌더링 검수까지 재현 |
| P2 | 로컬 현황 화면 | 읽기 전용 현황·미결 판단·근거·산출물 탐색, 개인정보 기본 비공개 |
| P2 | GitHub·운영 연결 | 우선 커밋·CI·릴리스 근거 연결, 쓰기는 권한과 기존 승인 범위에 따라 수행 |
| P2 | 문서·배포 일원화 | README·웹 가이드·PDF·설치 패키지의 기능/버전 불일치 검사 |
| 이후 | 조직 협업 서비스 | 실제 다중 사용자·접근 제어·동기화 요구 확인 후 범위 결정 |

P0는 가능한 항목부터 현재 계열의 보완 버전으로 먼저 제공할 수 있다. v2에서는 구조 변경이 필요한 P1을 묶되, P2 전체를 최초 공개의 전제조건으로 삼지 않는다.

### 권장 마일스톤

1. **M0 — 신뢰성 및 이행 기반:** 위 재현 사례를 자동 회귀 검증으로 만들고, 기존 데이터 유지와 업데이트 경로를 검증한다.
2. **M1 — 실제 실행 흐름:** 업무 프로필·릴리스 범위·실행 결과·재개를 연결한다. SI와 제품 각각의 한 흐름을 끝까지 확인한다.
3. **M2 — 제안 제작 완주:** 가상 RFP와 자체 제작 템플릿으로 원문 판독→평가 대응→제안서·발표→전체 렌더링→수정→제출 준비를 확인한다.
4. **M3 — 사용성과 공개 품질:** 현황 탐색, 설치·업데이트·복구 안내, 배포 패키지, 문서·PDF 버전 일치를 검증해 공개한다.

코딩 기간보다 호스트별 도구 차이, 실제 파일 제작, 한글 폰트·표·장문 처리, 기존 프로젝트 이행이 일정의 주요 불확실성이다. 실제 설계와 M0 결과 없이 날짜를 확정하지 않는다.

## 9. 기존 사용자와 프로젝트 이행

- 플러그인·마켓플레이스·스킬 식별자는 기본적으로 유지하고 브랜드 표시명과 구분한다. 호환성 조치는 검증된 설치·업데이트 경로를 따른다.
- `schema_version: 1` 프로젝트를 발견하면 지원 범위와 변경 항목을 먼저 계산한다. 현재 엔진은 스키마 1만 허용하므로 새 엔진의 버전별 읽기·이행 정책이 필요하다.
- 기존 문서·고객 자료·ID·승인·해시는 보존한다. 새 기본형을 기존 프로젝트 위에 복사하지 않는다.
- 이행 전 백업과 변경 목록, 이행 후 비교 결과를 남긴다. 실패하면 전체 복구하며 사용자 추가 편집을 지우는 복구는 거부한다.
- 새로 필요한 근거를 과거 작업에 임의로 생성하지 않는다. 이전 결과는 ‘v1 기준 검증’으로 보존하고 추가 확인이 필요한 부분을 드러낸다.
- 업무 프로필과 릴리스 범위를 도입할 때 현재 요구사항 중 어느 항목이 이행 범위인지 분명히 한다. 새 범위가 승인 기준에 미치는 영향도 기록한다.
- 명령·데이터 형식 변경은 마이그레이션 안내와 호스트별 인수인계에 반영한다. 사용자가 CSV·JSON을 직접 고치게 하지 않는다.

## 10. 제품 수준 검증 계획

기존 59개 테스트는 유지하고 신규 기능의 계약·실패 경로를 검증한다. 이번 가상 재현은 정식 회귀 테스트로 옮길 후보이며, 아직 테스트 스위트에 추가한 상태는 아니다.

| 시나리오 | 통과 조건 |
| --- | --- |
| SI 제안 | RFP 원문·평가 대응·제안서·발표·대본·검수 결과가 같은 버전으로 연결 |
| 제품 반복 개발 | 첫 릴리스 범위를 검증·배포하고 미래 백로그는 미완료로 유지 가능 |
| 문서 예외 | 혼합 스캔·긴 표·한글·손상 문서·지원하지 않는 형식을 정확히 처리 |
| 중단·재시도 | 작업 중단 후 재개해 중복 기록/산출물이 생기지 않고 실제 결과와 일치 |
| 동시 수정 | 누락·오래된 revision 거부, 정상 수정 및 추가 편집 보존 |
| 변경 후 검토 | 관련 입력·산출물·범위가 바뀌면 영향받은 검토만 추적해 갱신 |
| 두 호스트 | 동일 가상 업무의 입력·결과 규격을 각각 확인하고 도구 차이를 정확히 보고 |
| v1 이행 | 백업·변경 미리보기·정상 이행·실패 복구·기존 ID/이력 비교 통과 |
| 배포·공개 | 설치 패키지에서 고객 자료 제외, 공개 사이트에 업무 데이터 미포함 |

개발자가 가상 RFP·DOCX·PPTX·혼합 PDF를 만들어 자동 검증과 실제 호스트 실행 검증을 수행한다. 사용자의 개인 템플릿 제출이나 개발 테스트 참여를 제품 완료의 전제조건으로 두지 않는다. 실제 사용자 자료로 확인하는 단계는 동의를 받은 별도 사용성·재현 품질 평가다.

추후 측정할 값은 최초 결과까지의 시간, 미판독 페이지 수, 평가 대응 누락, 파일 생성·렌더링 성공 여부, 중단 후 재개 성공 여부, 사용자에게 요청한 업무 판단 수, 수정 후 재검수 누락이다. 측정 전 목표 달성률이나 시간 절감률을 홍보 수치로 쓰지 않는다.

## 11. 최초 v2 범위 제안

최초 v2에서는 **P0 보강 + 업무 프로필/릴리스 범위 + 실행·재개 + 실제 제안 제작 한 흐름**을 완료 대상으로 삼는다. 공개 사이트는 기존 가이드의 진입점으로 활용하고, 로컬 현황 화면은 이후 단계 또는 검증된 최소 탐색 기능부터 제공한다.

중앙 SaaS, 자체 모델 호출 인프라, 필수 API 키, 모든 업무 도구 연동, 자동 다중 에이전트 조직, 모든 문서 형식의 완전한 디자인 재현은 최초 범위에서 제외하는 것을 권고한다. 이 선택은 현재 로컬·오픈소스·호스트 기반 사용 방식을 유지하면서 핵심 경험을 검증하기 위한 범위 제안이다.

다음 설계 산출물은 v2 기능 목록만 나열하기보다 **사용 시나리오·작업 상태 규격·업무 프로필·데이터 이행 명세·완료 검증표**로 만드는 것이 적절하다. 이 분석에서는 엔진·스킬·버전을 변경하지 않았고, 보고서를 공개 저장소에 푸시하거나 사이트에 배포하지 않았다.
