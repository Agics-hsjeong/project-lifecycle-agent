# 프로젝트이음 관제 워크스페이스

관제는 Codex·Claude Code에서 진행하는 작업을 **보는 화면**이다. 사용자는 AI 코딩 도구에서 목표를 요청하고 질문·방향 수정·필요한 판단을 전달한다. 에이전트는 역할을 선택하고 구현·검토·수정을 이어간다. 관제에서 검토자 이름이나 수정 프롬프트를 매번 입력하지 않는다.

이 안내는 **2.0.0-beta.9** 기준이다. 기존 사용자는 플러그인을 업데이트하고 새 세션에서 로딩 버전과 호스트 훅 연결을 확인한다. 훅 신뢰 확인이 나오면 변경 내용을 검토한 뒤 호스트 UI에서 허용한다.

## Windows의 관측 지연과 복구

관리 도구는 native 관측 파일의 읽기·쓰기를 같은 잠금으로 조율합니다. 이 파일은 업무 변경 저널과 분리해 원자 교체하므로 관측 저장 충돌이 업무 원장의 미완료 저널을 만들지 않습니다. 짧은 Windows 공유 충돌은 유한 재시도하고, 오래 열린 외부 읽기 핸들이나 지속적인 권한 오류는 실제 원인을 표시합니다.

외부 읽기가 계속되면 새 활동 반영은 늦어질 수 있습니다. 관제의 마지막 정상 수신과 관측 오류·지연 표시를 함께 확인하세요. 보관한 이벤트와 로그 커서는 충돌이 해소된 후 다시 처리합니다. 임의로 완료율을 올리거나 미완료 업무 저널·잠금을 삭제하지 않습니다. 업무 커밋 마지막에 저널을 삭제하는 짧은 Windows 공유 충돌도 유한 재시도합니다. 지속 오류로 실제 업무 저널이 남은 경우에는 이를 보존하고 기존 복구 검사를 따릅니다. [재현·실제 검증 기록](WORKSPACE-OBSERVATION-VALIDATION.md)

## 접근 거부가 계속될 때

Windows에서 새 파일 소유자의 권한만 남으면 공유 충돌이 사라진 뒤에도 관측 파일 읽기가 거부될 수 있다. beta.8은 native 파일을 저장하기 전에 프로젝트의 기존 보안 기준으로 빈 임시 파일의 접근 규칙을 준비·검증한다. 권한을 확인할 수 없거나 사용자 지정 정책과 맞지 않으면 저장을 중단하고 실제 이유를 남긴다.

“이음, 공유 충돌과 접근 권한을 구분해 진단하고, 엔진의 안전 복구 조건을 모두 만족할 때만 생성 관측 파일을 복구한 뒤 갱신을 확인해줘”라고 요청한다. 에이전트는 정확한 native 파일의 스키마·상속 정책·내용 해시 등을 대조하고 조건이 맞을 때만 명시적 `repair-access` 엔진 경로를 사용한다. 별도의 엔진 메타데이터 접근 문제는 `repair-project-access`에서 정확한 상대 경로를 명시하고 전 대상 스키마·해시를 검증해 같은 바이트를 보존하는 경우만 복구한다. 입력 원본·코드·일반 문서·pending 저널·기존 폴더 권한은 복구하지 않으며 조건이 맞지 않으면 거절한다. 새로 생성하는 빈 출력 폴더만 위임 전에 보안을 준비한다. [보안 저장·복구의 상세 범위](ENGINE.md)

관제 표시에서만 접근 불가인 과거 산출물 부모와 TASK 입력의 파일/폴더 판독 오류를 해당 항목의 `unavailable`로 구분한다. 상대 경로·비공개 경로 보호를 먼저 적용하며, 다른 작업·로그 조회를 유지하기 위한 표시 처리다. 완료 근거·게이트·영수증·일반 파일 해시 검증과 다운로드는 기존처럼 엄격하며 접근 불가를 정상 증거나 승인으로 계산하지 않는다.

## 사용 흐름

1. 실제 고객 프로젝트를 Codex 또는 Claude Code에서 연다.
2. “이음으로 이 기능을 만들어줘. 역할별 진행 상황도 관제에서 보여줘”라고 요청한다.
3. 현재 호스트가 필요한 역할과 실제 작업·산출물·선후 관계를 연결하고 관제 화면을 연다.
4. 사용자는 기존 AI 대화에서 요청을 이어간다. 관제에서는 진행 중·대기 중·완료된 작업, 현재 담당자, 최근 행동, 실제 검증 결과를 본다.

사업 방향·접근 권한·외부 발송·운영 배포처럼 사람의 판단이 필요한 일은 AI가 대화에서 설명한다. 이미 요청받은 범위의 내부 설계·코드 검토 때문에 관제 승인 버튼을 추가하지 않는다. AI 검토 통과를 사람의 승인이나 수주로 기록하지 않는다.

## B안 화면 사용

왼쪽 메뉴에서 실행 현황·워크플로우·작업 지도·타임라인·산출물로 이동한다. 실행 현황의 작업 표에서 전체/진행/대기/완료를 선택하고 검색·필터로 범위를 좁힌다. 완료 비율은 선택한 실행 범위 기준이며 상태·검색 필터와 무관하다. 최근 실행과 전체 기록의 집계를 구분해 확인한다. 데스크톱에서는 행을 선택하면 오른쪽 현재 행동과 로그가 바뀌고, 작업 상세 보기로 전체 기록·파일 Diff를 연다. 모바일에서는 작업을 누르면 전체 화면 상세가 열린다.

표 아래 역할별 작업 흐름은 실제 실행 시도와 활동 시각을 사용한다. 시각이 없으면 미보고로 표시하며 계획 일정을 실행 시간처럼 만들지 않는다. 좁은 화면에서는 시간표 안쪽만 가로로 스크롤한다. 별도 타임라인 메뉴의 WBS는 예정 일정과 실제 실행 기록을 함께 확인하는 뷰다.

## QA 실패에서 재검증까지 — 2.0.0-beta.9

실행 현황 상단의 수정 흐름에서 현재 실행의 실패 원인, 개발 수정 요약, 재검증 결과와 차수를 바로 읽습니다. 예를 들어 QA 1차 실패, 개발 수정, QA 2차 통과를 기록 순서로 표시합니다. 통과한 뒤에도 최초 실패 카드를 남기며 별도 승인 입력을 요구하지 않습니다. 좁은 화면에서는 같은 순서로 세로 배치하며, 실행 현황의 상단 정보와 함께 페이지를 스크롤해 읽습니다.

각 카드의 설명은 엔진에 저장된 실제 실행 메모입니다. 개발 작업이 실패 근거의 같은 경로·SHA-256을 전달받은 기록이 있을 때만 수정 관계로 연결합니다. 같은 실행에 있거나 시간상 가까운 작업이라는 이유만으로 묶지 않습니다. 기록 시각이 없으면 미보고로 남기며, 최종 근거가 바뀌면 현재 검증 통과와 구분합니다. 전체 기록의 실패를 현재 실행의 진척도에 섞지 않습니다.

시도 이력은 읽기 전용 스냅샷에 추가로 표시합니다. 원장 결과·완료 영수증·진척도 계산은 변경하지 않으며, 표시 상한으로 일부 기록이 생략되면 그 수를 알립니다. 원문 로그·자격 증명·숨은 추론은 이 요약으로 전송하지 않습니다.

## 화면에서 보는 것

- **실행 현황:** 선택한 범위의 진행 중·대기 중·완료 작업과 근거에 따른 완료 비율을 표시한다. 전체 기록 집계는 별도로 남는다.
- **역할별 활동:** 실제 실행된 작업자와 담당 작업, 현재 행동, 마지막 활동 시각을 표시한다. 사용 가능한 18개 역할을 활성 작업자 18개로 표시하지 않는다.
- **활동 로그:** 파일 수정, 도구 실행, 검증 시작/결과, 역할 간 전달, 수정·재검증을 시간순으로 확인한다. 숨은 추론이나 확인하지 않은 대화를 꾸며내지 않는다.
- **워크플로우·작업 지도·WBS:** 같은 작업의 선후 관계, 요구사항·산출물 연결, 예정·실제 일정을 탐색한다.
- **상세 패널:** 선택한 작업의 실제 활동, 파일·Diff, 의존성, 일정·사용량을 읽는다. 상태만 보여주지 않고 대기 또는 실패 이유를 함께 보여준다.

정확히 측정할 수 없는 개별 작업 진척률은 임의의 퍼센트로 올리지 않는다. 완료 작업 비율, 경과 시간, 실제 완료된 검증 그룹 등 확인한 값만 보여준다. 실행기가 연결되어 대기하는 것과 모델이 실제 작업하는 것을 구분한다. 호스트가 전달하지 않은 토큰·비용은 미집계다.

## 두 가지 연결

기본은 **현재 AI 코딩 호스트의 시작·종료 이벤트와 명시적인 작업 연결**이다. 주 에이전트가 TASK와 역할을 위임에 연결하고 호스트 관측기가 실제 native 작업자 ID·세션·공개 행동을 수집한다. 같은 역할의 작업이 여러 개면 역할명으로 추정하지 않는다. 연결되지 않은 다른 채팅·도구 내역을 화면이 임의로 읽지는 않는다.

별도 실행이 필요하면 로그인된 네이티브 CLI를 사용하는 로컬 실행기를 연결할 수 있다. 이 실행기는 허용 범위와 검증 기준이 등록된 작업을 이어가며 native tool/action을 관제에 전달한다. 기존 앱 대화창에 메시지를 주입하는 방식은 아니다. 한 프로젝트에 하나의 실행기만 연결하고 두 방식의 같은 작업을 중복 실행하지 않는다.

[호스트 연결과 실행 범위](AUTOMATIC-EXECUTION.md)에서 설치·기록·검토·복구 규약을 확인한다.

## 최근 실행과 전체 기록

기본 진척은 **최근에 선언한 RUN** 기준이다. 가장 최근 실행이 실패하거나 증거가 바뀌었어도 그대로 표시한다. 과거에 성공한 RUN을 골라 현재 성공처럼 보이지 않는다. 명시한 실행 범위가 있으면 그 작업 ID 목록으로 집계하고, 별도 RUN이 없으면 프로젝트 전체 작업을 사용한다.

과거 실패·차단·변경됨 작업과 독립 실행은 전체 기록에 남는다. 예를 들어 최신 RUN 3개가 모두 완료여도 전체 기록에 실패가 있으면 **최근 실행 3/3, 전체 기록 4/9**처럼 구분한다. 검색 결과가 1개라고 완료율의 분모가 1로 바뀌지 않는다. TASK를 새 STEP에 연결한 이전 결과도 이력에서 확인할 수 있다.

## 실행 중과 검증 완료

역할 카드의 작업자 ID는 세션에 속한 실제 native ID다. 화면에는 원장 상태와 실행 상태를 함께 연결한다. **실행 종료·결과 확인 중**은 worker 프로세스가 끝났지만 근거 기록이 아직 완료되지 않은 상태다. 완료·검증 통과는 기존 TASK/RUN의 실제 파일·입력·영수증 검사를 따라야 한다. 실패나 변경된 증거가 native 종료만으로 통과가 되지 않는다.

호스트가 한동안 이벤트를 주지 않았다는 이유만으로 종료를 단정하지 않는다. 마지막 관측 시각과 관측 지연을 확인한다. 모델 내부 추론이나 생성 중인 토큰으로 가짜 진행률을 만들지 않는다.

작업 제목은 다음 행동과 별도로 보존한다. 다음 행동이 “없음” 또는 완료 메모로 바뀌어도 제목은 남으며, 구형 원장은 연결된 RUN 제목·최초 미완료 작업 기록으로 읽기 시 복원한다. 복원할 근거가 없으면 역할과 TASK ID를 사용한다. 관제 조회만으로 고객 기록을 수정하지 않는다.

## 기존 승인 기록과 안전 경계

이전 개발본의 명시적 사람 게이트와 결정 이력은 삭제하지 않는다. 새 관제는 이를 기본 진행 절차로 요구하지 않으며, 사용자가 내부 검토 자동화를 요청한 기존 프로젝트는 `required:false`로 해당 관제 게이트를 관찰 대상으로 전환할 수 있다. 이 전환은 사람 승인 기록을 생성하지 않는다. 사업 단계 승인과 운영 권한은 별개다.

오래된 입력·파일 충돌·실패한 검증은 실제 원인과 다음 역할에 연결한다. 코드 결함은 허용된 개발 경로 안에서 QA→개발→QA로 수정한다. 같은 원인의 반복 실패에는 제한을 두고, 인증·권한·외부 장애를 무한 재시도하지 않는다.

## 로컬 데이터와 연결

원장·산출물은 프로젝트 폴더에 남는다. loopback 서버는 127.0.0.1만 사용하고 조회·호스트 보고 capability를 분리한다. 접속 링크의 토큰과 로컬 원시 로그는 공유·커밋하지 않는다. 고객 자료를 공개 데모에 업로드하지 않는다.

연결이 끊기면 화면에 마지막 갱신과 연결 상태를 표시한다. 컴퓨터·호스트·실행기가 동작해야 새로운 활동이 들어온다. 연결 실패를 시뮬레이션으로 바꾸지 않는다.

[실제 검증 기록](WORKSPACE-OBSERVATION-VALIDATION.md)

## 자동 실행 안정화 작업본

프로젝트 데이터 수신과 실제 실행기 연결을 구분한다. 실행기 시작 재시도·실패 이유를 표시하고, 원장을 기록하는 동안의 일시적 조회 지연에는 마지막 정상 화면과 수신 시각을 보존한다. 정상적인 다음 조회로 복구한다. 파일·Diff는 선택한 파일의 해시가 바뀌면 다시 읽고 오래된 응답은 표시하지 않는다.

별도 CLI 실행기의 독립 검증에는 로컬 Codex sandbox CLI가 필요하며 모델 API는 호출하지 않는다. Windows는 MXC 지원이 필요하다. 에이전트가 환경과 `--verification-executable` 연결을 확인하며, 사용할 수 없는 격리를 비격리 테스트로 대체하지 않는다. 원본 충돌·인증·검증 환경 오류는 실제 이유를 남기고 중지한다.
