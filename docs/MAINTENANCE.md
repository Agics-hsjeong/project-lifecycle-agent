# 회사 표준과 프로젝트 관리

## 공통 표준과 개별 사업 구분

blueprint/에는 재사용 가능한 회사 표준만 둔다. 고객별 계약·견적·개인정보·코드는 projects/<프로젝트>/에 둔다. 고객마다 별도 저장소를 쓰는 편이 접근권한을 분리하기 쉽다. 이 스타터팩 폴더 전체를 공개 저장소로 올리기 전에는 projects/와 입력 자료 포함 여부를 확인한다.

기본형 버전은 blueprint/project.json의 starter_version과 CHANGELOG에서 함께 관리한다. 생성 도구는 버전을 그대로 복사하며 기존 프로젝트를 자동 갱신하지 않는다.

## 기본형 업데이트

1. 변경 이유와 영향을 CHANGELOG에 기록한다.
2. blueprint의 문서·규칙·원장 열을 수정한다.
3. tools 및 테스트와 README의 명령 예시를 함께 확인한다.
4. 새 시험 프로젝트를 생성해 지침 로딩과 check/context를 확인한다.
5. 기존 프로젝트에는 차이 목록을 만들고 필요한 부분만 적용한다. 고객 작성 내용과 승인 기록은 보존한다.

## 매주 진행 관리

- `status`로 여러 프로젝트의 단계·초안·작업 현황을 확인한다.
- PM은 기한·의존성·리스크·범위 변경을 확인한다.
- 다음 단계로 넘어가기 전 `check --stage <단계>`를 실행하고 사람의 검토 기록을 남긴다.
- 납품 버전에서 요구사항·문서·코드·테스트·배포 버전의 연결을 확인한다.
- 운영 중 장애와 변경 요청은 별도 ID로 추적하고 다음 릴리스에 연결한다.

## 최소 적용과 확장

1인·소규모 사업은 문서를 합쳐 작성할 수 있다. deliverables.csv의 경로를 통합 문서로 변경하고 각 산출물 ID와 책임은 유지한다. `not_applicable`은 적용하지 않는 이유와 검토 기록을 함께 남긴 경우에 쓴다.

계약상 필수 산출물이나 검토 절차가 있으면 그것을 우선 반영한다. 자체 서비스는 RFP 대신 사업 가설·사용자 문제·성공 지표를 입력으로 삼고, 수주 대신 투자·진행 결정으로 착수한다.

## 앞으로 제품으로 확장하는 순서

1. 실제 프로젝트 1건으로 양식·역할·완료 기준을 조정한다.
2. 조직 공통 규칙·기술 스택별 규칙을 분리하고 기본형을 안정화한다.
3. 저장소·디자인·문서 도구를 연결한다.
4. 필요하면 API 실행기와 권한·감사 로그를 구축한다.
5. 여러 프로젝트의 일정·공수·원가·품질 현황을 보는 관리 화면을 구축한다.

이 목록은 확장 계획이며 현재 버전에 구현된 기능 목록이 아니다.
