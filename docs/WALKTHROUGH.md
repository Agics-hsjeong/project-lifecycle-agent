# 예시: 고객 포털 사업

아래는 사용 방법을 보여주는 가상 사례다. 실제 RFP·견적·검수 결과가 아니다.

## 1. 사업 검토

```text
inputs/의 RFP를 분석해줘. 원본 페이지/절 번호를 붙여
필수 요구사항, 평가 항목, 제출물, 일정, 제약, 확인 질문을 추출해줘.
요구사항마다 REQ-001부터 ID를 부여하고 requirements.csv에 기록해줘.
근거 없는 기능·공수·가격은 확정하지 말고 가정으로 분리해줘.
```

예: `REQ-001 / RFP 3.2절 / 고객이 본인 신청 상태를 조회 / 타인 신청 조회 차단 및 3개 상태 표시`.

## 2. 제안·착수

```text
제안 역할로 요구사항 대응표, 수행 범위, 제외 범위, 일정과
역할별 공수 산정 초안을 작성해줘. 근거 자료와 불확실성을 표시해줘.
수주 후에는 최종 계약·협상 결과와 제안서의 차이를 착수 문서에 반영해줘.
```

자체 서비스라면 고객 검증 결과와 성공 지표를 기준으로 MVP 범위를 정한다.

정성제안·발표 준비는 다음처럼 요청한다.

```text
RFP 지정 목차와 평가기준에 맞춰 정성제안서 제출본을 작성해줘.
평가항목 대응표와 발표자료, 슬라이드별 대본·예상 Q&A도 만들어줘.
원문 발표 시간과 파일 형식을 확인하고 실제 문서·슬라이드 전체를 렌더링해 검수해줘.
제안서·발표·산정의 수치를 대조하고 제출 전 점검과 남은 질문을 기록해줘.
```

에이전트가 EVAL→제안서 절, EVAL↔SLIDE를 연결하고 실제 제출 파일을 관리한다. 발표가 없는 경우에는 원문 근거로 제외 사유를 남긴다. 자세한 산출물 구분은 [제안 패키지 안내](PROPOSAL.md)를 따른다.

## 3. 설계부터 구현

```text
REQ-001의 화면 상태, 접근권한, API·데이터 구조, 수용기준을 설계해줘.
디자인·퍼블리싱·구현 결과 경로를 원장에 연결하고,
승인된 범위에서 작은 작업 단위로 진행해줘.
```

요구사항의 design_refs·implementation_refs·test_refs·deliverable_ids를 채운다. 여러 경로는 `;`로 구분한다. 폴더 대신 실제 파일 경로를 쓴다. 외부 디자인 링크는 버전을 명세 문서에 기록하고 그 로컬 명세 경로를 연결한다.

## 4. 검증과 납품

```text
REQ-001의 정상 조회·접근 거부·빈 목록·오류 상태를 검증해줘.
실행 환경, 명령, 결과와 증거 경로를 남기고 미실행은 구분해줘.
납품 목록에서 코드·문서·테스트·릴리스 버전을 대조해줘.
```

`check` 통과 후에도 QA와 인수 담당자가 내용과 증거를 확인한다. 운영 배포는 기존에 부여된 권한과 배포 절차에 따라 수행한다.

## 5. 유지보수와 AI 교체

```text
유지보수 역할로 장애 현상과 영향, 우회 방법, 원인 가설을 정리해줘.
승인된 변경 범위에서 수정·회귀 테스트·릴리스 준비를 진행해줘.
다음 Claude/Codex가 이어받을 수 있도록 HANDOFF.md를 갱신해줘.
```

장애 대응을 이유로 계약 범위나 운영 권한을 임의로 확대하지 않는다. 이미 합의된 긴급 대응 범위가 있으면 그 범위 안에서 진행한다.
