# 초기 관제와 자동 실행 검증 이력

> 이후 사용자 요구로 관제를 역할별 활동 관찰 화면으로 변경했다. 최신 결과는 [관찰형 검증 기록](WORKSPACE-OBSERVATION-VALIDATION.md)을 따른다. 아래는 이전 승인 중심 흐름의 검증 이력이다.

검증일: 2026-11-19 (Asia/Seoul). 소스 개발 작업본에서 검증했으며 **공개 배포·커밋·푸시·기존 플러그인 설치 갱신은 하지 않았다.** 아래 네이티브 테스트는 고객 자료가 없는 별도 합성 프로젝트로 수행했다.

## 이번 실제 E2E

Windows의 실제 Codex CLI 0.170.0과 Claude Code 2.1.327을 기존 로그인으로 실행했다. 가짜 모델 응답이나 수동 역할 수행을 네이티브 실행 결과로 계산하지 않는다. 두 프로젝트의 `project.json`, `registers/`, `state/`, 설계·코드·테스트 파일을 실제 loopback API에 연결했다. 브라우저 검토자는 Synthetic E2E reviewer로 명시했으며 실제 고객의 승인을 의미하지 않는다.

공통 검증 흐름:

1. 화면에서 설계에 수정 요청을 남긴다. 상주 실행기가 architect 역할로 실제 CLI 프로세스를 시작한다.
2. 모델이 설계를 수정하고 감독자가 계약 검증을 실행한다. 새 파일은 재검토 대기로 돌아오며 개발은 실행되지 않는다.
3. 화면에서 승인한다. 이후 별도 채팅·수동 claim·모델 호출 없이 실행기가 backend → QA를 순서대로 실행한다.
4. 완료된 설계에 다시 수정 요청한다. 영향받는 이전 결과를 stale로 표시하고 과거 명령과 실패 기록은 보존한다.
5. 실제 재작업을 완료한 뒤 다시 사람 승인을 기다린다. 화면에서 재승인하면 backend·QA를 새 generation 2로 실행한다.
6. 최종 산출물에서 독립 요구사항 검사와 생성 테스트를 부모 검증자가 다시 실행한다. 원본 RFP 바이트, 개별 게이트 승인, 사업 단계 discovery 유지를 확인한다.

Claude의 첫 QA가 문자열 하위 클래스의 `strip()` 재정의로 공백 사용자 검증을 우회하는 결함을 발견했다. 감독자는 실패를 기록하고 후속 완료를 차단했다. 이후 사람이 설계 게이트에 해당 반례를 수정 지시하고 재승인한 뒤, 새 backend·QA 실행이 결함을 해결했다. 이전 실패 명령은 삭제하지 않았다. Codex에서도 완료 후 같은 정책 보완과 재검증 흐름을 수행했다.

## 검증 중 고친 문제

- 실행 계획의 Python argv와 실제 인터프리터 경로를 구분해 검증 영수증이 등록 계약과 일치하도록 수정했다.
- 재시도마다 새 작업 사본과 시도 ID를 사용하고 이전 시도를 보존했다.
- Claude의 변경 없는 원본 인용을 생성 산출물과 분리했다.
- 생성된 검증 코드도 원본 프로젝트가 아닌 사본에서 실행하고, 승인·검증 기록은 넓은 reports 쓰기 범위에서도 변경을 거부했다.
- Windows 독립 CLI가 데스크톱 전용 Core 전송을 요청하던 충돌을 수정했다. 샌드박스·자동 승인 검토·기존 권한 정책은 유지하며 공식 샌드박스의 파일 읽기도 확인했다.
- 승인 API와 짧은 원장 잠금 경합을 제한 대기로 처리하되 오래된 revision·컨텍스트는 거절한다.
- 완료 후 새 수정 요청으로 영향받는 결과를 무효화하고, 새 승인 후 실제 새 명령/RUN을 만든다. 이전 RUN·실패 기록은 보존한다.
- 실패한 모델 호출도 실제 보고된 사용량만 원장에 남기고, 재시도별로 중복 없이 합산한다. 미제공 비용을 0으로 만들지 않는다.
- 완료된 게이트의 수정 요청 UX, 패널 크기 조절 ARIA 값, 선택된 WBS 행과 Diff 줄 번호 대비를 보완했다.

## 범위와 한계

네이티브 E2E는 Python 표준 라이브러리의 소규모 합성 프로젝트다. 여러 기술 스택·외부 API·클라우드 배포까지 검증한 것은 아니다. 격리 사본의 외부 의존성은 별도 준비가 필요하다. 이 실행기는 프로젝트당 한 호스트가 준비된 역할 작업을 순서대로 실행하며 병렬 스케줄러는 아니다.

모델의 인증·권한·사용 한도와 컴퓨터·실행기의 가동이 필요하다. 기존 앱 대화창에 메시지를 주입하지 않는다. 모바일 검증은 Edge headless 너비 에뮬레이션이며 실기기 검사나 전체 접근성 적합성 인증은 아니다. 검토자 이름과 로컬 capability는 사내 SSO·전자서명이 아니다. 이 관제 승인은 개별 산출물 승인으로 사업 단계 전체를 승인하지 않는다.

초기 연결 결함을 진단하며 생긴 실패는 이력을 보존한 명시 재시도로 복구했다. 수정 완료 후 각 브라우저의 마지막 재승인부터 backend·QA 완료까지에는 수동 호스트 디스패치를 하지 않았다. 실패 사용량 계측을 추가하기 전의 과거 실패 비용을 추정해 소급하지 않는다.

## 로컬 근거

- `automatic-execution/full-regression.log`: 전체 226개 회귀.
- `automatic-execution/native-execution-report.json`: 실제 세션·역할·새 세대·검증 영수증과 원본 불변 확인.
- `automatic-execution/native-browser-report.json`: 두 실제 프로젝트의 완료·데스크톱/모바일·접근성·오류 결과.
- `automatic-execution/package-verification.json`, `packaged-browser-report.json`: 검증 ZIP·압축 해제 공식 CLI·실제 관제 UI.
- `automatic-execution/projects/<host>/reports/runner/`: 실제 감독 영수증과 검증 로그.
- `automatic-execution/jobs/<host>/attempt-*/`: 원시 네이티브 응답·개별 시도·실패/성공 감독 영수증. 토큰이나 사용자 인증 자료를 공개하지 않는다.
- `workspace-validation/`: 이전 관제 연결·지도·WBS·스냅샷·SQL 검증 근거.
