# v2 기반 구현과 이행 안내

갱신일: 2026-11-23 · 릴리스 버전: **2.0.0-beta.10** · 설치 ID 유지

이 문서는 beta.10의 사용 기준과 Windows 관측 경합 처리 및 실제 실행 연결·현재 범위·제목 보존 및 기존 검증·보호·프로젝트 이행을 설명한다. 설치본은 에이전트에게 실제 로딩 버전을 확인하게 한 뒤 업데이트한다. 두 CLI에서의 자동 역할 실행·검증·이어하기 결과와 남은 호스트 제한은 [실제 검증 기록](HOST-VALIDATION.md)에 구분했다. 문서 제작·렌더링 품질과 운영 배포는 각 실제 업무의 자료·도구·권한으로 검수해야 한다.

## beta.10 여러 RUN·근거 접근·수집 상태의 일치

명시적으로 고른 작업 범위에 여러 RUN이 포함돼도 QA 실패 → 개발 수정 → 재검증을 실제 TASK/STEP과 같은 근거 경로·SHA-256, 실제 순서로 연결합니다. 단계마다 RUN과 시도 차수를 표시하며 범위 밖·대체된·모호한 이력은 현재 흐름에 섞지 않습니다.

기록된 실행 완료와 지금 읽어 확인할 수 있는 근거를 분리합니다. 접근 불가는 `unavailable`, 실제 내용 변경은 `changed`로 구분하며 접근 불가를 유효한 완료·승인 근거로 계산하지 않습니다. Windows 원 작성자는 선언된 생성 출력에 한해 기존 바이트·해시를 보존해 발행합니다. 입력 원본·민감 경로·다른 역할 자료·사용자 지정 권한은 바꾸지 않습니다.

수집 중 정상 경합을 연결 끊김으로 단정하지 않고 지속적인 접근·손상 오류는 경고로 남깁니다. 마지막 정상 기록과 미처리 이벤트·커서를 보존해 다음 수집을 이어갑니다. 실제 작업·HTTP 수신·브라우저 표시는 별도 근거로 검증하며 모든 환경의 무중단 실행을 보장한다는 뜻은 아닙니다. [관제 사용법](WORKSPACE.md)을 참고하세요.

## beta.9 QA 실패·수정·재검증 흐름

실행 현황 상단에서 실패 원인, 개발 수정 내용, 시도별 재검증 결과를 바로 읽는다. 최종 성공 뒤에도 최초 실패와 재시도 차수·실제 기록 시각을 보존한다. 현재 실행의 정확한 TASK/STEP 연결과 전달된 근거 경로·SHA-256이 일치하는 수정만 묶으며, 누락·모호한 이력을 추정하지 않는다. 최종 근거가 바뀐 상태는 현재 통과와 구분한다.

모바일 실행 현황은 개요·알림·카드가 함께 스크롤된다. 시도 이력은 읽기 전용 투영이며 원장 결과·진척도 계산·완료 영수증·보안 검증을 변경하지 않는다. 기존 프로젝트 문서나 원장을 이 기능 때문에 교체할 필요가 없다. [관제 사용법](WORKSPACE.md)을 참고한다.

## beta.8 Windows 보안 저장과 릴리스 검증

설치본의 새 Codex 세션에서 native 파일 교체 후 관제 호스트의 읽기가 지속 거부되는 원인을 추가 확인했다. 새 파일 소유자에 적용된 `OWNER RIGHTS`와 호스트 접근 권한을 구분하며, 재시도만으로 권한 문제를 해결됐다고 판단하지 않는다.

native 저장에는 프로젝트 루트 소유자를 보안 기준으로 명시한다. 빈 임시 파일의 DACL에서 소유자 권한 항목을 안정된 기준으로 준비·검증한 뒤 내용을 쓰고 교체한다. 다른 허용·거부 비트와 순서·상속 보호 상태를 보존한다. 사용자 지정 소유권 충돌이나 미확인·null DACL은 중단하며 소유권 강탈·광역 권한 추가는 하지 않는다.

기존 영향받은 생성 native 파일은 정확한 경로·schema 1·상속 항목만 존재·부모 정책 일치·상속 보호 해제·내용 바이트/해시 보존 조건이 모두 맞을 때 명시적 `repair-access` 엔진으로 복구한다. 추가 엔진 메타데이터 복구는 명시적 `repair-project-access PROJECT --path ...`에서 정확한 project/registers/state/events와 events에 등록된 history만 전 대상 스키마·바이트/해시 대조 후 처리한다. 입력·코드·일반 문서·pending 저널은 제외한다. 업무 commit/restore는 보안 기준을 전달하고 새 빈 폴더만 준비하며 기존 폴더 ACL은 유지한다. 사용자 보안 정책을 우회하지 않는다. [보안 저장·복구 상세](ENGINE.md)를 따른다.

실행기 부하 테스트의 승인 전제도 조회 부하·실행기 시작 전에 설정하도록 분리한다. 원래 확인하려는 두 작업의 자동 실행과 빈번한 조회 부하는 유지한다.

beta.7은 main CI가 통과한 뒤 태그했지만 릴리스 재검사의 Linux/Python 3.12에서 이 테스트 준비 단계가 잠금 제한 시간을 소진해 플러그인 배포가 차단됐다. 기존 태그는 재작성하지 않으며 새 beta.8의 반복 검사·CI·배포·설치 결과를 별도로 확인한다. beta.7 소스의 실제 작업 결과와 첫 시도 실패 기록은 [검증 기록](WORKSPACE-OBSERVATION-VALIDATION.md)에 보존한다.

## beta.7 Windows 관측 경합 처리

관측 JSON을 읽는 동안 Windows가 원자 교체를 거부하던 경로를 조정했다. 관리 읽기는 기존 쓰기 잠금과 직렬화하고 native 관측 저장은 업무 변경 저널을 사용하지 않는 단일 파일 원자 교체로 분리한다. 짧은 공유 충돌만 제한된 시간 재시도하며 지속 오류·기존 업무 미완료 저널을 숨기지 않는다.

업무 커밋 마지막의 `state/pending.json` 삭제도 정확한 저널 경로의 Windows 공유·접근 거부 오류만 최대 250ms 재시도한다. 지속 오류는 저널을 보존하고 표준 복구의 현재 파일 대조·충돌 검사를 적용한다.

외부 읽기가 오래 유지되면 새 관측은 지연될 수 있다. 마지막 완전한 관측 파일과 미처리 이벤트·로그 커서를 보존해 후속 수신에서 다시 처리한다. 역할 실행 종료는 계속 원장 검증과 구분한다. 실제 작업과 경합 재현의 결과는 [검증 기록](WORKSPACE-OBSERVATION-VALIDATION.md)에 별도로 기록한다.

## beta.6 실제 실행 연결과 기록 보존

호스트 세션별 실제 작업자 ID와 시작·종료 이벤트를 명시 TASK 위임에 연결한다. 원장 상태와 실행 상태를 분리하고, worker 종료만으로 완료·검증 통과를 기록하지 않는다. 최근 실행 진척과 전체 이력을 나누며 최신 실패·변경됨 RUN도 현재 범위에 남긴다. 새 실행·TASK 바인딩은 한 트랜잭션에 저장하고 이전 결과·영수증을 보존한다.

작업명은 다음 행동·완료 메모와 분리해 저장한다. 기존 프로젝트는 연결된 RUN과 최초 미완료 기록으로 제목을 읽기 시 복원하며 조회만으로 파일을 바꾸지 않는다. 업데이트 후 새 세션에서 로딩 버전·관제 연결을 확인한다. 변경된 훅 신뢰 검토가 나오면 호스트 UI의 검토를 완료해야 한다. 기존 고객 프로젝트와 승인·실패 기록을 덮어쓰지 않는다.

## beta.5 검증·보호·관제 품질 개선

코드 작업의 빈 검사 계획을 차단하고 검증 대상·계획·컨텍스트를 파일 해시로 연결한다. 읽기 전용 검증을 마친 고정 바이트만 반영하며 완료 직전 변경도 확인한다. 최소 입력·자격 증명 필터·로그 마스킹과 생성 작업자 경계를 적용한다. 별도 Claude 생성 실행기는 실제 검증한 Claude Code 2.1.327 이상을 요구한다.

외부 의존성은 lockfile과 전체 파일 해시에 결속한 승인 Python/Node 검증 환경을 사용한다. Windows 네트워크 차단 격리는 asyncio 내부 TCP 채널을 사용하는 ASGI TestClient를 지원하지 않는다. 등록 환경은 즉시 환경 오류로 끝내 자동 코드 수정을 막는다. 스키마·순수 로직의 격리 검증과 별도 신뢰 환경의 ASGI 통합 검증 범위를 구분한다.

관제는 데이터 수신·native 활동 보고·별도 CLI 실행기를 구분한다. 완료·실패·대기·제외와 감독자 검증·호스트 보고를 별도 표시하고 미보고 사용량을 0으로 채우지 않는다. 등록 산출물의 인증·SHA 기반 미리보기/다운로드와 모바일 세 가지 뷰·상세 패널을 제공한다. 실제 실행 및 남는 지원 범위는 [품질 개선 검증 기록](QUALITY-IMPROVEMENTS.md)을 확인한다.

## beta.4 관제·자동 실행 안정화

관제는 현재 프로젝트의 실제 작업·역할·파일·검증·실행 시간을 관찰한다. 내부 구현마다 사람 승인 폼을 요구하지 않는다. 현재 앱의 작업 보고와 별도 네이티브 CLI 실행기를 구분하고, HTTP 기록 수신과 실제 실행기 연결을 별도로 표시한다. 연결하지 않은 대화·숨은 추론을 수집한다고 주장하지 않는다.

- 준비 실패도 실제 실패 영수증으로 닫고, 소유 프로세스 종료 근거가 있는 고아 수신을 복구한다. 살아 있는 소유권을 빼앗거나 모델 작업을 임의로 중복 실행하지 않는다.
- 대기 작업의 선행조건·게이트 조회는 일관된 잠금 아래 수행한다. 실제 관리 잠금 경합만 최대 3초·40ms 간격으로 재시도해 짧은 기록 충돌 때문에 실행기가 종료되는 것을 줄인다. 계속 잠긴 경우 실패를 기록하고 종료하며 정책·경로·권한 오류는 즉시 전파한다. 작업을 가져올 때 최신 revision·context 검증도 유지한다.
- Windows 전체 프로세스 수명과 입력·최종 활동 수신 중 취소·제한 시간을 관리한다. 확장 DOS/UNC 접두사 비교와 잠금 삭제 경합을 좁게 처리하며 외부 경로·링크·지속적인 권한 거부는 계속 차단한다.
- 독립 검증은 로컬 Codex sandbox CLI의 OS 격리 안에서 실행한다. 모델 API는 호출하지 않으며 Claude 실행기에서도 같은 검증 도구를 사용한다. Windows는 MXC를 지원하는 Windows 11 환경이 필요하고 미지원 환경에서는 이유와 함께 실패한다. 비격리 fallback은 없다.
- 모델 사본 밖의 짧은 소유 임시 경로에 공개 Python 검증 런타임을 만들고 읽기 전용으로 연결한다. 원본·사용자 홈 읽기, 사본 밖 쓰기와 네트워크를 제한하며 자격 증명·설치 site-packages는 복사하지 않는다.
- 늦은 조회가 완료 상태를 되돌리지 않으며 파일 SHA 변경 시 열린 Diff를 갱신한다. 잘못된 snapshot은 반려하고 마지막 정상 화면을 보존한다. 원장 기록 중의 conflict는 갱신 대기로 표시하고 다음 조회로 복구한다.
- 모든 기준 입력의 원본·추출문 해시를 검사한다. PPTX는 실제 활성 목록으로 장수를 계산하고 HWPX는 본문 참조 순서를 따른다.

실제 Codex CLI 0.170.0·Claude Code 2.1.327에서 백엔드→QA를 추가 사람 결정 없이 완료했고 각 산출물을 새 사본의 strict MXC에서 다시 검증했다. 이번 실제 QA는 모두 통과해 자동 수정 분기는 발동하지 않았으며 해당 분기의 회귀 검증과 구분한다. [검증 범위](WORKSPACE-OBSERVATION-VALIDATION.md)와 [관제 사용법](WORKSPACE.md)을 확인한다.

## beta.2 자동 역할 실행

팀이라는 추가 요청 없이 복합 작업을 필요한 전문 역할에 자동 위임한다. 단순 질문·조회는 직접 처리하며 기존 단계·증거·승인 규칙을 유지한다. `$ieum`과 프로젝트별 Claude `/ieum` 별칭을 제공한다. 상세 동작과 실제 호스트 검증은 [역할별 안내](ROLE-AGENTS.md)를 확인한다.

## 사용자는 업무를 요청한다

다음처럼 요청하면 에이전트가 내부 도구·원장·검증을 처리한다. 아래 JSON과 명령은 에이전트·개발자를 위한 규격이며 사용자가 편집할 필요가 없다.

- “이 RFP로 SI 프로젝트를 시작하고, 내가 넣은 템플릿으로 제안서와 발표자료를 준비해줘.”
- “자체 제품 프로필로 시작하고, 첫 릴리스에는 REQ-001만 넣어줘. 이후 백로그는 남겨줘.”
- “계약에 추가된 산출물도 등록하고 검토·납품 목록에 연결해줘.”
- “운영 메모로 보관해줘. 요구사항이나 계약 범위를 바꾸는 자료는 아니야.”
- “중단된 작업의 결과 파일을 확인하고 유효한 지점부터 이어가줘.”
- “방금 관리 정보 수정 내용을 복원해줘. 내가 추가 편집한 부분은 덮어쓰지 마.”

| 입력 | XML DTD/엔터티 공통 차단. PDF 페이지별 판독 상태와 partial 상태. 미판독 기준 자료는 초반 단계 완료 차단 |
| 판독 보완 | 실제 호스트 판독 결과와 전체 페이지 목록을 input-review로 보관. 근거나 원본이 바뀌면 다시 확인 |
| 제출 PDF | 헤더 외에 선택적 pypdf의 실제 파싱·본문 스트림·페이지 수 검사. 파서가 없으면 검증 완료로 처리하지 않음 |
| 출력 검수 | artifact-review가 제출본·PDF·전체 PNG·호스트 내용/스타일 검수 근거를 연결. 변경 후 유효성 검사 |
| 코드·환경 | 기본 src와 의존성 잠금 파일의 변경 해시, 기획 이후 기술 설정을 검토에 연결 |
| 운영 메모 | 명시적인 operating_note는 사업 기준선 입력과 분리. 기존 입력의 용도를 중복 등록으로 바꾸지 못함 |
| 업무 프로필 | SI 11단계, 제품 6단계, UI 없는 API 9단계, 유지보수 6단계. 기존 프로젝트는 기본 11단계 유지 |
| 릴리스 | planning 이후 지정한 REL 범위의 요구사항으로 완료 판정. 미래 백로그는 proposed 상태로 보존 가능 |
| 차단 조건 | 단계별 TASK/RISK 선행조건. 작업은 실제 근거가 있는 done, 위험은 종료 근거 파일과 closed 필요 |
| 변경 보관 | 엔진이 쓰는 관리 파일의 변경 전 내용을 state/history에 지속 보관 |
| 복원 | undo-preview와 undo가 최신 revision·파일 해시·계획을 비교. 이후 수정이 있으면 덮어쓰기 거부 |
| 작업 실행 기록 | 입력·의존 단계·예상 출력·실행 횟수·근거·결과 key를 관리. 중복 결과 재반영과 오래된 결과의 재사용 방지 |
| 환경 | doctor의 ready는 관리 엔진 준비. 문서 제작·렌더링·OCR 등 호스트 기능은 별도 capability로 표시 |
| 현황 | dashboard가 로컬 reports/ HTML을 생성. 외부 전송 없음. 사용자 편집이 있으면 덮어쓰기 거부 |

## 프로필·릴리스 규격

신규 프로젝트의 에이전트는 실제 요청에 따라 init에 --profile si/product/api/maintenance를 지정한다. 생략하면 기존 11단계로 생성한다. project.json의 workflow가 없는 기존 프로젝트도 같은 방식이다. business_type과 methodology를 이름만 바꿔 프로필 변경으로 간주하지 않는다.

apply의 project.workflow 예시:

```json
{
  "profile": "product",
  "release": {"id": "REL-001", "requirement_ids": ["REQ-001"]},
  "blockers": {"release": {"tasks": ["TASK-001"], "risks": ["RISK-001"]}}
}
```

연결 ID는 실제 원장에 있어야 한다. 현재 단계를 제거하는 프로필 변경은 거부한다. 새 릴리스에서 앞선 단계로 돌아갈 때는 기존 rewind의 실제 변경 사유·근거를 사용한다. 과거 승인·범위가 계속 유효하다고 가정하지 않는다. 제품의 운영 진입 시에는 SI 인수 문서 대신 해당 릴리스의 승인된 산출물을 요구사항에 연결한다.

technical.source_roots에는 프로젝트 내부의 구체적인 코드 폴더·파일을 지정한다. 기본은 src와 일반적인 의존성 잠금 파일이다. 관리 기록·외부 경로는 지정하지 않는다. 10,000파일·64 MiB를 넘으면 범위를 조정한다. 이 검사는 모든 외부 서비스·저장소·동적 의존성을 자동 추적하는 기능은 아니다.

## 실행 계획·결과 규격

run-create는 아래 계획을 받는다. expected_revision에는 최신 inspect 값을 넣는다.

```json
{
  "expected_revision": "<latest-revision>",
  "key": "REL-001-proposal",
  "title": "제안서 초안과 검수",
  "requirement_ids": ["REQ-001"],
  "steps": [
    {"id": "STEP-001", "title": "제안 내용 작성", "depends_on": [], "inputs": ["inputs/sources/INPUT-001/rfp.txt"], "expected_outputs": ["working/proposal.md"]},
    {"id": "STEP-002", "title": "내용 검토", "depends_on": ["STEP-001"], "inputs": ["working/proposal.md"], "expected_outputs": ["reviews/proposal-content.md"]}
  ]
}
```

의존 단계는 앞서 정의한 단계여야 한다. 선행 단계의 expected_outputs는 생성 전에도 후속 입력으로 지정할 수 있다. 나머지 입력은 실제 존재해야 한다. key가 같은 동일 요청은 재생성하지 않고, 같은 key의 다른 계획은 거부한다.

run-result는 expected_revision/run_id/step_id/key/status/evidence_refs/notes를 받는다. 상태는 running, blocked, awaiting_decision, succeeded, failed, skipped다. 에이전트가 실제 도구로 작업을 수행하며 엔진은 명령 문자열을 실행하지 않는다.

- running을 먼저 기록한 뒤 실제 작업한다. 근거가 있는 succeeded만 완료로 처리한다.
- 입력과 동일한 파일을 완료 증거로 쓰지 않는다. 수정 작업은 명세를 입력으로, 수정한 코드·실행 결과를 출력 근거로 계획한다.
- 성공 시 예상 출력이 근거 목록에 있어야 하고, 실행 도중 입력이 바뀌면 성공을 거부한다.
- 적용 제외에는 실제 결정 근거가 필요하다. 사용자 결정을 만들어 기록하지 않는다.
- run-resume은 입력·근거·상위 단계의 유효성을 다시 계산한다. stale 결과와 실행 가능한 다음 단계를 반환한다.
- running 단계는 재개 조회만으로 다시 실행하지 않는다. 실제 작업 종료·실패 여부를 확인하고 결과를 기록한다.
- 같은 결과 key의 재전달은 이력을 중복 기록하지 않는다. 내용이 다른 재전달은 거부한다.

이 실행 계획은 작업 재개를 위한 제어·증거 기록이다. Markdown 계획의 완료만으로 실제 DOCX/PPTX·제출본 제작이 끝났다고 표시하지 않는다. 실제 파일 제작과 전체 렌더링·스타일·사실 검수는 기존 문서/발표 도구와 규약을 적용한다.

## 판독 결과 보완 규격

input-review에는 expected_revision, input_id, evidence_ref, page_count, pages를 보낸다. PDF는 실제 전체 페이지 수와 1부터 마지막까지의 목록이 필요하다. 비페이지 문서는 page_count: null, pages: []를 사용할 수 있다. 증거 파일에는 호스트가 실제로 읽은 결과·위치·누락 해소 내용을 기록한다. 단순한 “완료” 주장은 내용 확인을 대신하지 않는다.

새 RFP·정정·계약·요구사항 변경은 baseline으로 등록한다. 운영 메모로 분류해 변경 영향을 숨기지 않는다. 판독 실패 원본은 보존하며, 추출 텍스트와 시각 정보가 완전히 같다고 가정하지 않는다.

## 변경 이력과 복원 규격

제안 출력의 artifact-review에는 expected_revision/role/source_file/pdf_file/pages/review_ref를 전달한다. role은 qualitative 또는 presentation이며, pages는 `[{"page": 1, "image_ref": "qa/page-1.png"}]`처럼 실제 PDF의 모든 페이지를 포함해야 한다. 각 PNG의 청크·체크섬·압축 데이터와 페이지 목록을 검사한다. PNG는 일반적인 비인터레이스 형식을 사용한다. source_file은 proposal/package.json의 실제 제출 파일과 일치해야 한다. 내용·사실·스타일은 호스트가 전 페이지를 실제로 읽고 대조한 결과를 review_ref에 기록한다. PDF와 이미지가 같은 내용인지에 대한 의미 판단을 엔진이 자동 인증하는 것은 아니다.

명시적인 SI/API 업무 프로필의 제안 단계에는 정성제안서와 필요한 발표자료의 출력 검수가 필수다. 기존 프로필 없는 프로젝트에는 자동 강제하지 않지만 검수 기록을 등록하면 이후 변경을 검사한다. dashboard는 이 근거와 현재 단계·미완료·판독·실행 상태를 로컬에 보여주며, 공개 사이트와 별개다.

history는 이력 메타데이터를 반환한다. undo-preview --revision에는 복원할 apply 변경을 지정하고, 반환한 계획을 undo --file로 전달한다. 조회·파일 작성·실행은 에이전트가 수행한다.

계획은 목표 이력의 해시, 현재 revision과 파일 해시, 복원/삭제할 관리 파일 목록을 포함한다. 기존 파일을 수정했거나 계획 이후 상태가 바뀌었으면 중단한다. 승인·단계 변경·원본 등록은 undo로 취소하지 않고 실제 결정과 review/rewind를 사용한다. 복원도 새 이력이며 기존 이벤트를 삭제하지 않는다.

보관 대상은 엔진 관리 파일이다. 일반 도구로 편집한 코드·문서의 모든 버전, v1에서 이미 사라진 내용, 실제 운영 데이터·배포는 이 기능으로 복구하지 않는다. 이 부분은 실제 Git 커밋·산출물 보관·운영 복구 절차를 따로 갖춰야 한다. 변경 전 내용에는 고객 자료가 들어갈 수 있으므로 state/history도 고객 작업 공간에서만 보관한다.

## 기존 프로젝트 이행

1. 에이전트가 설치 경로·버전과 프로젝트의 실제 파일을 확인하고 기존 프로젝트의 백업 범위를 확인한다.
2. 스키마 1·원장 열·ID·현재 문서를 유지한다. 새 blueprint를 기존 폴더에 복사하지 않는다.
3. 모든 apply에 최신 revision을 보낸다. 첫 이벤트 이전에는 null이며 생략은 허용하지 않는다.
4. 프로필은 필요할 때 명시적으로 적용한다. 기본형 업데이트만으로 기존 단계 흐름을 바꾸지 않는다.
5. 코드·환경·추가 산출물 검사 범위가 강화돼 기존 검토가 무효화될 수 있다. 실제 근거로 재확인하고 기존 승인 기록을 고쳐 통과시키지 않는다.
6. 과거 버전의 보관 내용은 소급 생성하지 않는다. 새 엔진의 변경부터 history가 생긴다.
7. 기존 캐시·고객 자료·설정은 직접 교체하지 않는다. 실제 로딩 버전과 호스트별 설치·업데이트·프로필 사용을 확인한다.
8. 구형 입력 manifest에 추출문 해시가 없다면 에이전트가 원본과 추출문을 실제 대조한 뒤 input-review로 연결한다. 확인 전에는 단계를 승인하지 않으며 자동으로 고객 파일을 덮어쓰지 않는다.

## 남은 범위

전체 문서/발표의 공통 출력 검수 기록과 로컬 현황은 구현했다. 실제 다양한 템플릿으로 Word/PowerPoint를 제작·변환하고 스타일·사실을 평가하는 호스트별 행동 검증은 남아 있다. 여러 저장소·GitHub/CI 결과의 정형 연결, CR/INC 전용 원장, 원가·일정 계산, 조직별 정책·외부 협업 서비스는 이번 기반 구현에 포함하지 않았다. 알파 기반과 전체 v2 완성을 구분한다.

## 베타의 이행·설치 확인

에이전트가 doctor의 plugin_root·version·project_path·project_starter_version을 대조한다. 폴더를 옮긴 프로젝트는 새 경로에서 inspect와 run-resume을 실행하며, 저장된 상대 경로 근거는 계속 사용한다. 외부 참고 폴더는 실제 존재 여부를 다시 확인한다.

upgrade-preview는 최신 revision과 관리 파일 해시가 포함된 실제 변경 계획을 반환한다. upgrade는 이 계획이 최신 상태와 같을 때 project.json의 starter_version·updated_at만 변경하고 변경 전 원본을 state/upgrades에 보관한다. 이는 변경하는 관리정보의 백업이며 고객 코드·산출물 전체 백업이 아니다. 새 양식·프로필·문서·승인 파일을 자동 교체하지 않는다.

바로 되돌릴 때는 upgrade-restore-preview --upgrade-id의 계획을 upgrade-restore에 전달한다. 이후 사용자 편집이나 새 이벤트가 있으면 충돌로 중단한다. 복원도 새 감사 이력으로 남긴다. 기존 검토가 현재 엔진 기준으로 유효한지는 inspect에서 따로 확인한다.

로컬 플러그인은 허용 목록으로 생성한 ZIP을 풀어 두 호스트의 공식 marketplace/install 명령으로 연결한다. 개발 저장소 전체를 설치 캐시로 복사하지 않는다. PACKAGE.json이 있는 설치본의 doctor는 전체 파일 해시·버전을 검사한다. 설치 후 새 채팅/세션에서 스킬을 다시 로딩한다.
