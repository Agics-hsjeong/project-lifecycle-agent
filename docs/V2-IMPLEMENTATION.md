# v2 기반 구현과 이행 안내

갱신일: 2026-11-03 · 개발 버전: **2.0.0-beta.1** · 설치 ID 유지

이 문서는 현재 작업 소스에 구현한 기능을 설명한다. 공개 안정판·사이트·사용자 매뉴얼 PDF와 설치된 플러그인은 이 작업으로 자동 갱신되지 않는다. 최종 v2 공개판이 아니며, 실제 문서 제작·렌더링 품질과 두 호스트의 설치·행동 검증을 별도로 완료해야 한다.

## 사용자는 업무를 요청한다

다음처럼 요청하면 에이전트가 내부 도구·원장·검증을 처리한다. 아래 JSON과 명령은 에이전트·개발자를 위한 규격이며 사용자가 편집할 필요가 없다.

- “이 RFP로 SI 프로젝트를 시작하고, 내가 넣은 템플릿으로 제안서와 발표자료를 준비해줘.”
- “자체 제품 프로필로 시작하고, 첫 릴리스에는 REQ-001만 넣어줘. 이후 백로그는 남겨줘.”
- “계약에 추가된 산출물도 등록하고 검토·납품 목록에 연결해줘.”
- “운영 메모로 보관해줘. 요구사항이나 계약 범위를 바꾸는 자료는 아니야.”
- “중단된 작업의 결과 파일을 확인하고 유효한 지점부터 이어가줘.”
- “방금 관리 정보 수정 내용을 복원해줘. 내가 추가 편집한 부분은 덮어쓰지 마.”

## 프로필·릴리스 규격

신규 프로젝트의 에이전트는 실제 요청에 따라 init에 --profile si/product/api/maintenance를 지정한다. 생략하면 기존 11단계로 생성한다. project.json의 workflow가 없는 기존 프로젝트도 같은 방식이다. business_type과 methodology를 이름만 바꿔 프로필 변경으로 간주하지 않는다.

apply의 project.workflow 예시:

```json
{
  "profile": "product",
  "release": {"id": "REL-001", "requirement_ids": ["REQ-001"]},
  "blockers": {"release": {"tasks": ["TASK-001"], "risks": ["RISK-001"]}}
}
```

연결 ID는 실제 원장에 있어야 한다. 현재 단계를 제거하는 프로필 변경은 거부한다. 새 릴리스에서 앞선 단계로 돌아갈 때는 기존 rewind의 실제 변경 사유·근거를 사용한다. 과거 승인·범위가 계속 유효하다고 가정하지 않는다. 제품의 운영 진입 시에는 SI 인수 문서 대신 해당 릴리스의 승인된 산출물을 요구사항에 연결한다.

technical.source_roots에는 프로젝트 내부의 구체적인 코드 폴더·파일을 지정한다. 기본은 src와 일반적인 의존성 잠금 파일이다. 관리 기록·외부 경로는 지정하지 않는다. 10,000파일·64 MiB를 넘으면 범위를 조정한다. 이 검사는 모든 외부 서비스·저장소·동적 의존성을 자동 추적하는 기능은 아니다.

## 실행 계획·결과 규격

run-create는 아래 계획을 받는다. expected_revision에는 최신 inspect 값을 넣는다.

```json
{
  "expected_revision": "<latest-revision>",
  "key": "REL-001-proposal",
  "title": "제안서 초안과 검수",
  "requirement_ids": ["REQ-001"],
  "steps": [
    {"id": "STEP-001", "title": "제안 내용 작성", "depends_on": [], "inputs": ["inputs/sources/INPUT-001/rfp.txt"], "expected_outputs": ["working/proposal.md"]},
    {"id": "STEP-002", "title": "내용 검토", "depends_on": ["STEP-001"], "inputs": ["working/proposal.md"], "expected_outputs": ["reviews/proposal-content.md"]}
  ]
}
```

의존 단계는 앞서 정의한 단계여야 한다. 선행 단계의 expected_outputs는 생성 전에도 후속 입력으로 지정할 수 있다. 나머지 입력은 실제 존재해야 한다. key가 같은 동일 요청은 재생성하지 않고, 같은 key의 다른 계획은 거부한다.

run-result는 expected_revision/run_id/step_id/key/status/evidence_refs/notes를 받는다. 상태는 running, blocked, awaiting_decision, succeeded, failed, skipped다. 에이전트가 실제 도구로 작업을 수행하며 엔진은 명령 문자열을 실행하지 않는다.

- running을 먼저 기록한 뒤 실제 작업한다. 근거가 있는 succeeded만 완료로 처리한다.
- 입력과 동일한 파일을 완료 증거로 쓰지 않는다. 수정 작업은 명세를 입력으로, 수정한 코드·실행 결과를 출력 근거로 계획한다.
- 성공 시 예상 출력이 근거 목록에 있어야 하고, 실행 도중 입력이 바뀌면 성공을 거부한다.
- 적용 제외에는 실제 결정 근거가 필요하다. 사용자 결정을 만들어 기록하지 않는다.
- run-resume은 입력·근거·상위 단계의 유효성을 다시 계산한다. stale 결과와 실행 가능한 다음 단계를 반환한다.
- running 단계는 재개 조회만으로 다시 실행하지 않는다. 실제 작업 종료·실패 여부를 확인하고 결과를 기록한다.
- 같은 결과 key의 재전달은 이력을 중복 기록하지 않는다. 내용이 다른 재전달은 거부한다.

이 실행 계획은 작업 재개를 위한 제어·증거 기록이다. Markdown 계획의 완료만으로 실제 DOCX/PPTX·제출본 제작이 끝났다고 표시하지 않는다. 실제 파일 제작과 전체 렌더링·스타일·사실 검수는 기존 문서/발표 도구와 규약을 적용한다.

## 판독 결과 보완 규격

input-review에는 expected_revision, input_id, evidence_ref, page_count, pages를 보낸다. PDF는 실제 전체 페이지 수와 1부터 마지막까지의 목록이 필요하다. 비페이지 문서는 page_count: null, pages: []를 사용할 수 있다. 증거 파일에는 호스트가 실제로 읽은 결과·위치·누락 해소 내용을 기록한다. 단순한 “완료” 주장은 내용 확인을 대신하지 않는다.

새 RFP·정정·계약·요구사항 변경은 baseline으로 등록한다. 운영 메모로 분류해 변경 영향을 숨기지 않는다. 판독 실패 원본은 보존하며, 추출 텍스트와 시각 정보가 완전히 같다고 가정하지 않는다.

## 변경 이력과 복원 규격

제안 출력의 artifact-review에는 expected_revision/role/source_file/pdf_file/pages/review_ref를 전달한다. role은 qualitative 또는 presentation이며, pages는 `[{"page": 1, "image_ref": "qa/page-1.png"}]`처럼 실제 PDF의 모든 페이지를 포함해야 한다. 각 PNG의 청크·체크섬·압축 데이터와 페이지 목록을 검사한다. PNG는 일반적인 비인터레이스 형식을 사용한다. source_file은 proposal/package.json의 실제 제출 파일과 일치해야 한다. 내용·사실·스타일은 호스트가 전 페이지를 실제로 읽고 대조한 결과를 review_ref에 기록한다. PDF와 이미지가 같은 내용인지에 대한 의미 판단을 엔진이 자동 인증하는 것은 아니다.

명시적인 SI/API 업무 프로필의 제안 단계에는 정성제안서와 필요한 발표자료의 출력 검수가 필수다. 기존 프로필 없는 프로젝트에는 자동 강제하지 않지만 검수 기록을 등록하면 이후 변경을 검사한다. dashboard는 이 근거와 현재 단계·미완료·판독·실행 상태를 로컬에 보여주며, 공개 사이트와 별개다.

history는 이력 메타데이터를 반환한다. undo-preview --revision에는 복원할 apply 변경을 지정하고, 반환한 계획을 undo --file로 전달한다. 조회·파일 작성·실행은 에이전트가 수행한다.

계획은 목표 이력의 해시, 현재 revision과 파일 해시, 복원/삭제할 관리 파일 목록을 포함한다. 기존 파일을 수정했거나 계획 이후 상태가 바뀌었으면 중단한다. 승인·단계 변경·원본 등록은 undo로 취소하지 않고 실제 결정과 review/rewind를 사용한다. 복원도 새 이력이며 기존 이벤트를 삭제하지 않는다.

보관 대상은 엔진 관리 파일이다. 일반 도구로 편집한 코드·문서의 모든 버전, v1에서 이미 사라진 내용, 실제 운영 데이터·배포는 이 기능으로 복구하지 않는다. 이 부분은 실제 Git 커밋·산출물 보관·운영 복구 절차를 따로 갖춰야 한다. 변경 전 내용에는 고객 자료가 들어갈 수 있으므로 state/history도 고객 작업 공간에서만 보관한다.

## 기존 프로젝트 이행

1. 에이전트가 설치 경로·버전과 프로젝트의 실제 파일을 확인하고 기존 프로젝트의 백업 범위를 확인한다.
2. 스키마 1·원장 열·ID·현재 문서를 유지한다. 새 blueprint를 기존 폴더에 복사하지 않는다.
3. 모든 apply에 최신 revision을 보낸다. 첫 이벤트 이전에는 null이며 생략은 허용하지 않는다.
4. 프로필은 필요할 때 명시적으로 적용한다. 기본형 업데이트만으로 기존 단계 흐름을 바꾸지 않는다.
5. 코드·환경·추가 산출물 검사 범위가 강화돼 기존 검토가 무효화될 수 있다. 실제 근거로 재확인하고 기존 승인 기록을 고쳐 통과시키지 않는다.
6. 과거 버전의 보관 내용은 소급 생성하지 않는다. 새 엔진의 변경부터 history가 생긴다.
7. 기존 캐시·고객 자료·설정은 직접 교체하지 않는다. 최종 배포 전 호스트별 설치·업데이트·프로필 사용을 별도로 검증한다.

## 남은 범위

전체 문서/발표의 공통 출력 검수 기록과 로컬 현황은 구현했다. 실제 다양한 템플릿으로 Word/PowerPoint를 제작·변환하고 스타일·사실을 평가하는 호스트별 행동 검증은 남아 있다. 여러 저장소·GitHub/CI 결과의 정형 연결, CR/INC 전용 원장, 원가·일정 계산, 조직별 정책·외부 협업 서비스는 이번 기반 구현에 포함하지 않았다. 알파 기반과 전체 v2 완성을 구분한다.

## 베타의 이행·설치 확인

에이전트가 doctor의 plugin_root·version·project_path·project_starter_version을 대조한다. 폴더를 옮긴 프로젝트는 새 경로에서 inspect와 run-resume을 실행하며, 저장된 상대 경로 근거는 계속 사용한다. 외부 참고 폴더는 실제 존재 여부를 다시 확인한다.

upgrade-preview는 최신 revision과 관리 파일 해시가 포함된 실제 변경 계획을 반환한다. upgrade는 이 계획이 최신 상태와 같을 때 project.json의 starter_version·updated_at만 변경하고 변경 전 원본을 state/upgrades에 보관한다. 이는 변경하는 관리정보의 백업이며 고객 코드·산출물 전체 백업이 아니다. 새 양식·프로필·문서·승인 파일을 자동 교체하지 않는다.

바로 되돌릴 때는 upgrade-restore-preview --upgrade-id의 계획을 upgrade-restore에 전달한다. 이후 사용자 편집이나 새 이벤트가 있으면 충돌로 중단한다. 복원도 새 감사 이력으로 남긴다. 기존 검토가 현재 엔진 기준으로 유효한지는 inspect에서 따로 확인한다.

로컬 플러그인은 허용 목록으로 생성한 ZIP을 풀어 두 호스트의 공식 marketplace/install 명령으로 연결한다. 개발 저장소 전체를 설치 캐시로 복사하지 않는다. PACKAGE.json이 있는 설치본의 doctor는 전체 파일 해시·버전을 검사한다. 설치 후 새 채팅/세션에서 스킬을 다시 로딩한다.
