# 단계와 완료 기준

단계는 업무의 기준선이다. 한 번 지나가면 돌아갈 수 없는 순서를 뜻하지 않는다. 구현·검증은 작은 요구사항 묶음으로 반복하고 설계 변경은 CR/ADR과 추적 원장에 반영한다.

## 단계 정의

| 코드 | 입력 | 필수 산출물 ID | 내용상 완료 기준 | 기본 검토 책임 |
| --- | --- | --- | --- | --- |
| discovery | SI: RFP / Product: 가설·조사 | DEL-001 | 원본·요구·질문·진행 타당성과 책임자 정리 | 사업/제품 책임자 |
| proposal | 검토 결과·평가/사업 기준 | DEL-002;DEL-003;DEL-015;DEL-016;DEL-017;DEL-018 | 정성제안서·평가 대응·발표자료·대본/Q&A·산정·제출 점검, 실제 제출 파일·발표 시간·근거 정합성 | 사업/제품 책임자 |
| kickoff | SI: 최종 계약 / Product: 진행 결정 | DEL-004 | 범위·성공지표·역할·일정·완료/인수기준 확정 | PM·발주/제품 책임자 |
| planning | 착수 범위·요구 원장 | DEL-005;DEL-006 | 화면·업무·데이터·권한·API·비기능 요구와 수용기준 연결 | 제품·기술 책임자 |
| design | 기획·설계 | DEL-007 | 디자인 토큰·주요 화면·모든 상태·반응형 검토 | 디자인 책임자 |
| publishing | 디자인 명세 | DEL-008 | UI 구현과 명세 일치, 상태·접근성·반응형 검증 | 프런트엔드 책임자 |
| implementation | 확정 요구·설계·UI | DEL-009 | 범위 내 구현, 리뷰, 변경·테스트 근거 연결 | 기술 책임자 |
| verification | 수용기준·구현 결과 | DEL-010 | 테스트 결과·결함·미해결 위험과 인수 판단 근거 확보 | QA·인수 담당자 |
| release | 검증 결과·운영 준비 | DEL-011 | 배포/복구 리허설, 실행 권한, 실행·관측 결과 기록 | 배포 책임자 |
| handover | 배포 버전·검수 결과 | DEL-012;DEL-013 | 납품 목록·인수·사용/운영 매뉴얼·계정 이전 완료 | 발주/제품·운영 담당자 |
| maintenance | 운영 인수·지원 합의 | DEL-014 | 지원 범위·연락·장애/변경/회귀/정기 점검 절차 확립 | 운영 책임자 |

Product의 proposal은 사업 실행안·MVP 투자 판단 문서다. 제출·계약 관련 항목은 적용 제외 사유를 적는다. UI가 없는 사업은 디자인·퍼블리싱 산출물을 not_applicable로 검토하고 tailoring에 남길 수 있다.

제안 패키지가 활성화된 새 프로젝트의 proposal 필수 산출물은 위 여섯 가지다. 정성제안서 본문과 실제 제출본, 평가항목 대응표, 발표자료 구성과 PPTX/PDF, 발표 대본·예상 Q&A, 제출 점검표를 함께 관리한다. 발표가 없는 사업은 원문/합의 근거로 DEL-016·017을 적용 제외하고 proposal/package.json에도 사유를 기록한다. 자체 서비스는 정성제안서를 사업 실행안, 발표를 투자/내부 의사결정 피치로 조정한다.

평가항목 EVAL과 발표 SLIDE를 proposal/package.json에서 연결한다. 이 파일은 apply의 proposal 항목으로 갱신한다. 발표 시간·실제 파일·평가 대응·역방향 연결을 검사하지만 내용과 디자인 검수는 실제 문서/슬라이드 렌더링으로 수행한다.

## 단계 진행 절차

1. PM은 입력·현재 상태·관련 요구사항을 읽고 다음 작업과 담당 역할을 정한다.
2. AI는 해당 단계 문서를 채우고 요구사항·산출물·작업 원장을 갱신한다.
3. 내용 검토를 받아 산출물 상태를 approved로 기록한다. 검토자는 원문·코드·로그를 확인한다.
4. reviews.csv에 단계·결정·검토자·일시·근거 파일·사유를 남긴다. 적용 제외는 사유가 필요하다.
5. `check`로 구조적 누락을 확인한다. PM은 검사 결과와 내용 검토를 함께 보고 다음 단계를 결정한다.
6. 엔진의 advance로 current_stage·updated_at과 HANDOFF.md를 기록한다. 현재·이전 검토가 유효해야 이동한다. 승인과 실행 결과를 만들어 넣지 않는다.

이전 단계로 돌아가면 변경 영향이 있는 산출물을 in_review로 돌리고 관련 검토 기록을 추가한다. 보류/실주/중단은 project.json의 tailoring과 HANDOFF에 사유·잔여 의무를 남긴다.

## 방법론 조정

- 기본 hybrid: 단계별 기준선 검토 + 작은 기능 단위 반복 개발.
- waterfall: 단계별 검토와 변경 통제를 강화한다. 검증 계획은 기획 시 작성한다.
- agile: backlog와 주기별 목표·리뷰를 운영한다. 최소 범위·수용기준·납품 증거를 유지한다.

project.json의 methodology는 관리 표기다. 도구가 Scrum 의식이나 개발 일정을 자동 실행하지 않는다. 단계 생략·병합·반복 주기·검토 책임은 tailoring에 이유와 결정 근거를 기록한다.

## 구조 점검 범위

`check`는 현재 단계의 필수 산출물 상태, 파일·미작성 표시, 검토 근거 파일, 요구사항 추적 경로를 검사한다. 초안 문서에서 `TODO`를 모두 해소해야 한다. 모르는 내용을 지워 통과시키지 말고 질문·보류 사유를 적고 검토한다.

planning 이후 설계 경로, implementation 이후 구현 경로, verification 이후 테스트 경로, handover 이후 납품 산출물 연결이 필요하다. 범위 제외(deferred)는 사유와 책임자의 단계 검토 근거로 관리한다. `check`는 이전 모든 단계가 완료되었는지 또는 의미상 테스트가 충분한지 판정하지 않는다.
