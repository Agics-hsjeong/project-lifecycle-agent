# Project Lifecycle

사용자는 목표와 자료를 제공한다. 파일 생성, 입력 등록, 상태 점검, 기록 갱신은 에이전트가 수행한다. 사용자에게 셸 명령·JSON 편집·CSV 작성을 일상 절차로 넘기지 않는다.

이 스킬은 전체 플러그인의 일부다. 플러그인 루트는 이 SKILL.md에서 두 단계 위이며 [관리 도구](../../tools/starter.py)와 [기본형](../../blueprint/AGENTS.md)을 함께 포함한다. 스킬 폴더만 단독 복사하면 자동 생성 도구를 사용할 수 없다.

## 프로젝트 시작

1. 현재 작업 공간과 사용자에게서 받은 RFP/아이디어를 확인한다. 기존 project.json이 있으면 기존 기록을 읽고 이어간다. 프로젝트가 여러 개면 이름을 확인하고, 명확한 경우 다시 묻지 않는다.
2. 새 프로젝트는 사용자가 허용한 작업 공간 안에 만든다. 기본 위치는 작업 공간의 projects/<사업 slug>다. 플러그인 설치 폴더나 캐시에 고객 프로젝트를 만들지 않는다.
3. 사용 가능한 Python 3.10+로 도구를 직접 실행한다. 위치는 실제 로딩된 플러그인 경로에서 구한다. 아래 `<...>`는 실행 시 실제 값으로 치환한다. 경로는 셸에 맞게 인자로 안전하게 전달한다.

```text
python <plugin-root>/tools/starter.py init --workspace <사용자 작업 공간> --name <사업명> --slug <영문 사업 ID> --type si --rfp <원본 파일>
```

자체 서비스는 `--type product`, 원본 파일이 없으면 `--rfp`를 생략하고 제공받은 아이디어를 프로젝트 inputs에 기록한다. Python이 없으면 사용 가능한 파일 도구로 기본형을 새 폴더에 복사하고 정보를 입력한다. 도구를 쓸 수 없을 때만 실제 제한을 설명한다.

4. AGENTS.md, project.json, HANDOFF.md와 process 문서를 읽는다. 사업 유형·목표·현재 단계를 자료에서 채우고 모르는 담당자·가격·계약 조건은 미정으로 남긴다.
5. 원본을 읽고 근거 페이지/절, 사실, 가정, 질문을 구분한다. 읽을 수 없는 형식은 읽었다고 보고하지 않는다. 가능한 도구로 추출하고 실제로 변환할 수 없을 때에만 필요한 자료를 요청한다.
6. discovery 산출물과 요구사항 원장을 실제 파일에 작성한다. 관리 폴더만 생성하고 업무가 끝났다고 하지 않는다. 중요한 사업 질문은 진행 가능한 분석과 초안을 작성하면서 묻는다.

## 단계별 작업과 이어하기

현재 프로젝트의 process/WORKFLOW.md와 ROLES.md에서 필요한 단계·역할만 읽는다. 사용자 요청과 확정된 범위에 따라 산출물·코드·검증 작업을 진행하고 REQ/TASK/DEL 참조를 유지한다. `check`와 `context`는 에이전트가 내부에서 실행한다.

검토를 기다리는 분석·초안은 in_review까지 진행한다. 확정된 사용자 결정이나 원문 증거가 있을 때 원장과 단계 상태를 갱신한다. 체크 명령의 종료 코드 1은 미완성 보고이며 도구 오류와 구분한다. 새 검토 결정을 사용자 대신 만들어 승인하지 않는다.

AI를 바꾸거나 작업을 마칠 때 HANDOFF.md에 실제 변경 파일·브랜치/커밋·검증 결과·미실행·미결정·다음 행동을 기록한다. 후속 에이전트는 이 기록을 실제 파일과 대조한다. 역할 정의만으로 하위 에이전트를 실행하지 않는다.

## 외부 연결과 결과 보고

GitHub·Figma·문서·배포 도구가 연결되어 있고 요청 범위에 해당하면 실제 도구로 진행한다. 이미 부여된 권한을 반복 확인하지 않는다. 외부 발송·공개·운영 변경에는 사용자의 실제 지시와 대상 범위가 필요하다. 설치 후에도 호스트의 파일·도구 권한이 적용된다.

사용자에게는 완료한 산출물, 근거와 미결정 사항, 필요한 다음 판단을 짧게 보고한다. 내부 명령 실행 순서를 사용자가 수행해야 하는 절차처럼 설명하지 않는다. 플러그인 배포 저장소에 고객 프로젝트·RFP·비밀정보를 포함하지 않는다.
