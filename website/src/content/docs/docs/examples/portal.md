**A사 고객 포털은 설명을 위해 만든 가상 사례**입니다. 고객 원본·실적·계약 정보를 포함하지 않습니다. 아래 결과는 사용법을 보여주는 텍스트 기준안이며 실제 엔진 실행 증거나 제출 완료본이 아닙니다.

[예제 전체 ZIP 다운로드](/project-lifecycle-agent/downloads/customer-portal-example.zip) · [GitHub에서 원본과 결과 읽기](https://github.com/Agics-hsjeong/project-lifecycle-agent/tree/main/examples/customer-portal)

## 1. 입력: 무엇을 만들어야 하나요?

가상 RFP의 목표는 이메일·전화로 나뉜 고객 문의를 포털로 모으는 것입니다.

- 고객: 자신의 문의 등록·목록·상세·상태 확인.
- 담당자: 문의 분류·답변·상태 변경 이력.
- 공개: FAQ·공지 읽기.
- 품질: 역할별 권한, 반응형·키보드 접근성, 운영 인수 자료.
- 조건: 6주 가정, 10분 발표. 예산·인력·인증·알림·첨부·호스팅은 미확정.

## 2. 에이전트에게 시작을 요청하세요

예제 ZIP을 자신의 업무 공간에 풀고 RFP.md의 실제 경로를 알려줍니다.

```text
Project Lifecycle Agent로 이 가상 RFP의 고객 포털 사업을 시작해줘.
현재 업무 폴더에 새 프로젝트를 만들고 식별자는 portal-demo로 해줘.
원본·요구사항·평가기준·고객 질문과 제안 초안을 작성해줘.
가상 예제임을 표시하고 고객 승인·실적·테스트 결과는 만들어내지 마.
```

## 3. 결과 예시: 근거와 수용 기준

| 요구사항 | RFP 근거 | 수용 기준 예시 |
| --- | --- | --- |
| REQ-001 역할별 접근 | 2.1 | 고객 A가 고객 B의 문의를 UI·직접 요청 모두로 조회할 수 없음 |
| REQ-002 문의 등록·조회 | 2.2 | 필수값 검증 후 등록되고 자신의 목록·상세에 표시 |
| REQ-003 운영 이력 | 2.3 | 답변자·변경 시각·상태 이력을 남기고 허용 역할만 변경 |

위 ID는 설명용입니다. 실제 고객 프로젝트에서는 엔진이 배정한 ID를 사용합니다.

## 4. 제안과 발표를 연결합니다

| 평가기준 | 배점 | 제안서 절 | 발표 |
| --- | --- | --- | --- |
| 사업 이해·범위 | 25 | 사업 이해·수행 전략 | 1~2장 |
| 기능·권한·사용성 | 35 | 기능·기술 제안 | 3장 |
| 수행·품질 계획 | 25 | 수행 계획 | 4장 |
| 운영·인수 | 15 | 운영·인수 계획 | 5장 |

발표 구성은 사업 이해 1분, 전략 2분, 기능·권한 3분, 일정·품질 2분, 운영·인수 2분으로 **총 10분**입니다. 산정은 **40인일의 가정**으로, 실제 인력·조건을 확인한 뒤 재산정합니다. 이는 실적이나 납기 보장이 아닙니다.

제안 본문 예시: “권한·보관 정책과 미확정 범위를 먼저 확정하고 고객 등록→상태 확인, 담당자 분류→답변→상태 변경의 핵심 경로에 집중한다. 운영 문서는 구현과 병행해 인수로 연결한다.”

## 5. 자기 스타일로 실제 파일을 제작합니다

ZIP의 결과는 텍스트 초안입니다. 자기 DOCX·PPTX 참고 자료가 있다면 생성된 templates 폴더에 넣고 [템플릿 분석](../../guides/templates/)과 [실제 제안 패키지 제작](../../guides/proposal/)을 요청합니다. 원본의 디자인·작성 패턴을 분석했다고 이 예제만으로 주장하지 않습니다.

## 6. 다음 작업과 미완료도 남깁니다

예제의 인수인계에는 고객 답변, 승인, 편집본 제작·렌더링·비교 검수, 실제 테스트·배포·제출을 미실행으로 구분합니다. 이를 실제 프로젝트의 승인 기록으로 복사하지 않습니다.

예제 ZIP에는 RFP부터 요구사항, 제안 본문, 산정, 평가 대응, 발표·대본·Q&A, 제출 점검과 인수인계까지 9개 Markdown 파일이 있습니다.
