**역할명이나 “팀으로 처리해줘”라는 말을 덧붙이지 않아도 됩니다.** 프로젝트이음이 요청 내용·현재 단계·기존 결과를 확인하고 필요한 최소 역할과 실행 순서를 선택합니다. 이 안내는 **2.0.0-beta.10** 기준이며 이전 beta.1에는 포함되지 않습니다.

## 원하는 결과를 말하세요

```text
첨부 RFP로 정성제안서와 발표자료를 만들어줘.
MVP 범위와 기능 정책, 화면 흐름을 구체화해줘.
문의 등록·조회 기능을 구현하고 테스트해줘.
출시 전에 결함과 보안 문제를 점검해줘.
```

프로젝트이음을 명시하려면 Codex에서는 `$ieum`을 선택한 뒤 요청합니다. Claude Code는 고객 프로젝트에 짧은 별칭을 준비한 뒤 다음처럼 요청합니다.

```text
/ieum 문의 등록·조회 기능을 구현하고 테스트해줘
```

[처음 설치하고 RFP로 시작하기](../../quickstart/)

## 처음 한 번, 쉬운 명령을 준비하세요

Codex 또는 Claude Code에 **“프로젝트이음으로 시작하고 짧은 명령도 준비해줘”**라고 요청합니다. 환경 확인과 필요한 연결은 에이전트가 처리합니다.

| 사용하는 AI | 짧은 호출 | 알아둘 점 |
| --- | --- | --- |
| Codex | `$ieum` | 플러그인을 설치·활성화한 새 채팅에서 사용 |
| Claude Code | `/ieum` | 고객 프로젝트별 별칭 설정 후 해당 폴더를 열어 사용 |

Claude Code의 별칭은 `.claude/skills/ieum/SKILL.md`에 만들어집니다. 설치한 플러그인으로 요청을 전달하며 기존 동명 스킬·명령은 덮어쓰지 않습니다. 별칭 준비 전에는 `/project-lifecycle-agent:ieum`으로 진입할 수 있습니다. 개인·관리자 설정이나 호스트 제한으로 명령이 보이지 않으면 에이전트에게 실제 로딩 경로·버전을 확인하게 하세요.

기존 `$project-lifecycle`, `/project-lifecycle-agent:project-lifecycle` 호출도 유지합니다. 저장소와 설치 ID를 새로 바꿀 필요는 없습니다.

## 어떤 역할이 선택되나요?

| 요청 예시 | 필요한 역할의 예 |
| --- | --- |
| RFP와 내 템플릿으로 제안서·발표자료 제작 | 제안 전략 → 제안서·발표자료 제작 → 결과 검수 |
| 서비스 기획 구체화 | PO → 기능 명세 → UX 리서치·정보설계 |
| 모바일 화면 사용성 개선 | UX·UI → 프론트엔드 → QA |
| 기능 구현과 테스트 | 필요한 기술·데이터 계약 확인 → 백엔드·프론트엔드 → QA·리뷰 |
| 출시 전 점검 | 요청 범위와 위험에 맞는 QA·보안·코드 리뷰 |

프로젝트에는 PO, 기능 명세, IA, 디자인 시스템, UI, UX 라이터, 시스템 아키텍트, DB, 백엔드, 프론트엔드·퍼블리싱, DevOps, QA, 보안 감사, 테크니컬 라이터, 오케스트레이터, 코드 리뷰, 제안 전략, 제안서·발표자료 제작의 **18개 역할 계약**이 있습니다.

모든 역할을 매번 실행하지는 않습니다. 질문·도움말·현황 조회·간단한 수정은 현재 에이전트가 직접 처리하고, 복합 구현·독립 검토에는 필요한 하위 에이전트를 실행합니다. “기획만” 요청했다면 개발·배포까지 범위를 넓히지 않습니다.

## 여러 역할은 어떻게 협업하나요?

1. 주 에이전트가 요청 범위·현재 단계·원문·요구사항을 확인합니다.
2. 필요한 역할에 실제 입력·담당 경로·기대 결과·수용 기준을 전달합니다.
3. API·데이터·디자인 토큰처럼 선행 계약이 필요한 부분부터 맞춥니다.
4. 독립 입력과 서로 다른 담당 경로가 있는 작업만 호스트 한도 안에서 병렬 실행합니다.
5. 실제 산출물·테스트·검토 결과를 확인하고 주 에이전트가 원장과 HANDOFF를 통합합니다.

같은 파일을 동시에 수정하지 않으며 하위 역할이 다시 팀을 만드는 재귀 위임은 하지 않습니다. 공통 원장과 진행 기록은 주 에이전트가 기존 엔진의 변경 검사·잠금 규칙으로 기록합니다.

## 결과에서 무엇을 확인하나요?

에이전트는 실제 만든 파일, 실행한 검증과 근거, 미완료·미결정, 다음 행동을 함께 보고합니다. 단순히 역할 계획을 적은 것과 실제 작업자를 실행한 것을 구분합니다. AI 검토 결과는 사람의 검수·사업 승인·운영 배포 허가를 대신하지 않습니다.

호스트가 하위 에이전트를 지원하지 않거나 인증·권한·동시 실행 한도에 막히면 제한과 대체 수행 방식을 안내합니다. 기본 작업자가 역할 계약을 받아 수행했는지, 현재 에이전트가 직접 처리했는지도 구분합니다. 설정 파일이 추가됐다는 사실만으로 역할 로딩·실행 성공을 주장하지 않습니다.

Codex와 Claude Code를 오갈 때에는 같은 고객 프로젝트 폴더를 엽니다. 공유되는 것은 파일과 HANDOFF이며 대화가 자동 동기화되지는 않습니다.

## 실제 호스트 검증

2026-11-19, Windows에서 Codex CLI 0.170.0과 Claude Code 2.1.327에 같은 가상 문의 조회 구현을 요청했습니다. 팀·역할을 지정하지 않아도 전문 작업자를 실행했고, 테스트는 각각 12개·9개가 통과했습니다. 새 세션 이어하기에서는 프로젝트 파일 변경이 없었습니다.

데스크톱 UI·모든 전문 역할·실제 회사 템플릿의 문서 품질까지 검증했다는 뜻은 아닙니다. [실제 요청·근거·실행 환경의 제한](https://github.com/Agics-hsjeong/project-lifecycle-agent/blob/main/docs/HOST-VALIDATION.md)을 확인하세요.

## 관제의 실제 작업자 연결

역할 계약과 실제 실행 인스턴스는 구분합니다. 에이전트가 TASK·역할·호스트 세션의 위임을 연결하고, 시작·종료 이벤트에서 실제 native ID를 결합합니다. 같은 역할만으로 여러 작업 중 하나를 추정하지 않습니다. 작업자가 끝나도 완료 근거가 없으면 결과 확인 중으로 표시합니다. [관제 사용법](../workspace/)
